# Набор данных показа

Отдельный Go-модуль задаёт общую модель набора, людей, каталог вариантов, объёмы по источникам и форматы результатов. Он использует только стандартную библиотеку и не импортирует backend. Ожидания будущих расчётов строятся здесь независимо от API и кода craftPulse. Генератор создаёт людей, план объёмов, модель задач и настройки показа. Модели репозиториев, MR, CI и загрузчики добавляются отдельными файлами следующих задач.

Нужен Go версии из `go.mod`. Команды выполняются из `demo-dataset/`:

```sh
go run ./cmd/dataset generate --seed 21 --out /tmp/model.json
go run ./cmd/dataset generate --seed 21 --out /tmp/model-again.json
cmp /tmp/model.json /tmp/model-again.json
go run ./cmd/dataset generate --seed 22 --out /tmp/model-other.json
```

Seed по умолчанию равен 21. Два одинаковых запуска дают одинаковые байты и SHA-256; другой seed меняет сгенерированные имена людей. ID людей и вариантов устойчивы при смене seed.

Период по умолчанию `[2026-01-01T00:00:00Z, 2026-12-01T00:00:00Z)`, as-of равен правой границе. Предложенная граница 1 ноября сдвинута, чтобы включить ноябрьское время загрузки MR и CI, которое задают сами источники. Для более поздней загрузки укажите `--as-of` до генерации и используйте ту же дату во всех частях manifest. Время хранится с точностью до секунды; исходный offset сохраняется отдельно. Периоды полуоткрытые, представление времени в UTC.

`model.json` содержит 20 участников команды первой организации, аккаунт второй организации и двух ботов. Для людей перечислены роли, ограничения repo/wiki и ожидаемое сопоставление логинов Jira DC, Confluence DC, GitLab и GitHub.com. `volumes` фиксирует 100 задач и 1000 событий (40/400 и 40/400 Jira DC, 20/200 импорт), 6 GitLab MR и 4 GitHub PR, 12 и 8 CI runs, по 25 Git-документов, 10 wiki-страниц, отдельную серию Jenkins. Закрытые объекты второй организации выделены отдельно. Размер страницы равен 10.

`variants` содержит 22 варианта: все строки раздела 6 среза MVP, историю по нескольким периодам, типам, размерам и версиям сроков, полное и неполное окно наблюдения переоткрытий, поздние события и повтор доставки. В записи есть источник, способ представления, ожидаемое поведение и ссылки V-xx из ТЗ. Каталог меняется централизованно в `dataset/catalog.go`; файлы моделей отдельных видов данных связывают свои ID с вариантами через `ObjectFile`.

## Модель задач и настройки показа

```sh
go run ./cmd/dataset generate --seed 21 --out /tmp/model.json \
  --tasks /tmp/tasks.json --task-objects /tmp/dataset-objects/tasks.json --settings /tmp/settings.json
```

Команда сначала строит и проверяет все части, затем пишет файлы и печатает SHA-256 каждого. Флаги `--tasks`, `--task-objects` и `--settings` необязательны: без них пишется только `model.json`.

`tasks.json` по `schemas/tasks.schema.json` содержит проекты, 101 задачу и 1 010 событий: 40/400 и 40/400 в проектах Jira DC `PA` и `PB`, 20/200 в проекте импорта `IMP`, 1/10 в закрытом проекте `SEC` второй организации. У проекта перечислены статусы с API-категорией источника, типы, размеры, команды и resolutions. Первое событие задачи `created` несёт начальные статус, тип, размер и команду; остальные события - `field_change` поля `status`, `resolution`, `type`, `size`, `team` или `flagged` с прежним и новым значением. ID события `<ID задачи>/eNN` устойчив, время хранится в UTC с исходным offset автора, `observed_time` задан только у событий, которые источник доставляет позже. Блокировка задаётся статусом `Blocked` и флагом `flagged = Impediment`; у PA-3 они перекрываются (V-41).

Задачи вариантов потока заданы явно и не зависят от seed: `PA-1`-`PA-18`, `PB-1`-`PB-6`, `PA-7` и `IMP-2`-`IMP-7` проекта импорта. Остальные задачи распределены по периоду с предысторией с декабря 2025 года, их тип, размер, время и исход задаёт seed. Чтобы объём событий проекта совпал точно, в их работу добавляются циклы `In Progress` → `In Review` → `In Progress`. Статус `Legacy QA` намеренно не сопоставлен. В `variants` перечислены задачи каждого варианта с источником Jira DC или универсального импорта; `multi-period-history` содержит все задачи с первым началом и первым принятым завершением внутри периода, их не меньше 20. `--task-objects` пишет те же связи в формате `schemas/objects.schema.json` для команды `manifest`.

`settings.json` по `schemas/settings.schema.json` содержит то, что подтверждают на шаге 2 показа: правила сопоставления в форме `MappingRule` API для `jira-dc-1` и `universal-1` (статусы, resolutions, типы, `code_required_type` для Story и Bug, размер с порядком, команда, флаг блокировки `blocked_flag`), версии целевых сроков команды по типу и размеру (Story S: v1 2 дня с 2026-02-01, v2 4 дня с 2026-07-01), окно переоткрытий T23 версии 1 в 30 дней и 10 задач для предпросмотра. Имена статусов и полей - значения набора; загрузчик заменяет их на ID, которые назначит источник.

## Сборка manifest

Схемы JSON находятся в `schemas/`: модель, объекты видов данных, часть manifest источника, общий manifest и ожидаемые значения. Поля обязательны, неизвестные поля, повторные ключи и пропущенные nullable-поля отклоняются CLI. Семантические проверки дополнительно проверяют время, уникальность и связи. Схемы не заменяют эти проверки.

Каждый загрузчик пишет отдельный JSON в каталог частей источников. Часть содержит URL без учётных данных, edition/version, точные queries/scopes, backfill, as-of, полноту, страницы/cursors, SHA, event/observed time с offset, версии mapping/calculation/parser/tool, хэши rules/config/DB и очищенных файлов, пути ожиданий. Для неприменимых SHA и namespace используется пустая строка, для пустых коллекций - массив или объект.

Идентичность источника - кортеж `organization_id`, `instance_id`, `object_kind`, `native_ns`, `native_id`. Связь `dataset_id` с этим кортежем появляется только после загрузки. Один отображаемый ключ разных instances не объединяет объекты. Файлы видов данных содержат `objects` и связи `variants`; команда строит сводку «вариант - ID объектов» и проверяет ссылки:

```sh
mkdir -p /tmp/dataset-sources /tmp/dataset-objects
go run ./cmd/dataset manifest --model /tmp/model.json \
  --sources /tmp/dataset-sources --objects /tmp/dataset-objects \
  --out /tmp/manifest.json
```

Пустые каталоги дают каркас manifest с пустыми источниками и связями. Это не подтверждение загрузки или покрытия вариантов. После появления моделей и загрузчиков команда объединяет их части; модель, период и as-of должны совпадать.

## Сверка ожиданий

Файл по `schemas/expected.schema.json` содержит записи со стабильным ID, показателем и версией определения, областью, фильтрами, периодом, шагом `week`/`month`, as-of, единицей, значением, числителем, знаменателем, n, состоянием данных, когортой ID и интервалами. Неопределённые числа передаются как JSON `null`; числа в строках запрещены. Длительности задаются в секундах без округления. Поддерживаются `ASSESSED`, `BOUNDED`, `PROVISIONAL`, `UNKNOWN`, `NOT_EVALUATED`, `NOT_APPLICABLE`.

```sh
go run ./cmd/dataset compare expected.json actual.json
```

Команда сравнивает все поля, печатает каждое расхождение и итоговое число. Код выхода 0 означает совпадение, 1 - ошибку входа или расхождения. Числа сравниваются точно, порядок записей и ID когорты не влияет на результат. Порядок интервалов и значений фильтра сохраняется. Отчёт показывает имена полей и индексы без значений пользовательского ввода. Тест CLI проверяет ноль расхождений на одинаковых файлах и три расхождения при замене значения, интервала и добавлении лишнего ID.

## Секреты и проверки

Пароли и токены запрещены в моделях, manifest, очищенных файлах и выводе. Загрузчики читают credentials из файлов вне набора, зашифрованных владельцем стенда через SOPS + age. Учебные secret-marker будущих fixtures собираются при запуске из частей; значения, похожие на действующие секреты, не хранятся литералами. Генератор не читает credentials и не обращается к сети.

```sh
gofmt -l .
go vet ./...
go test -race ./...
go build ./...
golangci-lint config verify
golangci-lint run --timeout=5m
golangci-lint fmt --diff
```

Линтер версии 2.15.0 запрещает импорты backend через depguard. Отдельный `go.mod` также исключает зависимость на модуль backend. CI выполняет эту ногу при изменениях набора или общих workflow и включает результат в обязательный `ci`.
