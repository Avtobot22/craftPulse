Запросы Jira идут через `https://api.atlassian.com/ex/jira/{cloudId}`, запросы Confluence - через `https://api.atlassian.com/ex/confluence/{cloudId}`.

Токен сборщика предназначен для импорта. Контроль под сборщиком вызвал `GET /rest/api/3/user/viewissue/search` с `accountId` каждой роли, `maxResults=100` и одним из параметров `projectKey=CPA` или `issueKey=CPA-1`. Все шесть запросов вернули `200` за 1047-1500 мс. Оба фильтра включили две роли A и исключили B. Поиск по `issueKey` включил роль A без доступа к `CPA-1`, хотя прямое чтение вернуло ей `404`. ## Решение по Q-10

В продакшене выдача Jira Cloud закрыта по умолчанию. Сбор может продолжаться. Проект Jira открывается только после проверки AC-12 и NFR-011 для подключения. Нужны пользовательский OAuth и отдельное свежее подтверждение проектного права и ограничения каждой задачи. При неопределённости `CheckAccess` возвращает `unknown`. Недоступные задачи и их вклад исключаются из выдачи, включая сохранённые срезы, прямые ссылки и выгрузки. Это правило закреплено в [разделе 13.5 ТЗ](../../docs/technical-specification/technical-specification.md#135-проверка-прав-в-источниках).

Прямое чтение и адресный `BROWSE_PROJECTS` дали разрешение в серии на 95-й секунде после отзыва. Обновление TTL по этим ответам и сверка по ночному расписанию не подходят для допуска. Webhook можно использовать для раннего закрытия и сверки. Сквозная проверка подтверждает, что после удаления из группы, смены схемы проекта и нового ограничения задачи ни одна поверхность не выдаёт её данные или вклад позже 60 с. Отдельно проверяются потеря уведомления, недоступность прав, перезапуск и повторное открытие после свежей сверки.

## Повтор прогона

Из корня репозитория запусти [source_checks.py](source_checks.py) с копией [stand.example.json](stand.example.json). Нужен Python 3.10+ и доступ по HTTPS к выбранному источнику. В копии плана укажи адреса экземпляра и идентификаторы тестовых проектов, пользователей и объектов. Замени `...-accountId` на ID тестовых ролей из стендового перечня. Переменные `CP91_*_BEARER` получают собственный OAuth access token роли, `CP91_ATLASSIAN_BASIC` - Base64 от пары email и API-токена сборщика, `CP91_GITLAB_TOKEN` - PAT `read_api` из комплекта #87.

```sh
python deploy/source-checks/source_checks.py stand.local.json --source jira_a_allowed --source confluence_a_allowed --source atlassian_discovery
python deploy/source-checks/source_checks.py stand.local.json --source jira_user_search
python deploy/source-checks/source_checks.py stand.local.json --source atlassian_collection --interactive
python deploy/source-checks/source_checks.py stand.local.json --source gitlab --interactive
```

В проверке отзыва зафиксируй исходное членство и положительные ответы. От имени оператора удали тестовую роль из группы Jira указанным запросом, подтвердив отсутствие через `GET /rest/api/3/group/member?groupId={id}`. С тем же OAuth-токеном опрашивай оба проекта и ограниченную задачу не менее 60 с. Зафиксируй первый запрет и все последующие ответы. Верни членство `POST /rest/api/3/group/user?groupId={id}` с телом `{"accountId":"..."}`, затем проверь восстановление чтения. Режим `gitlab_blocked_fixture` запускай отдельно между выдачей и снятием временного Reporter для заблокированной тестовой учётной записи в проекте 7. Для прямого прогона на стенде вызови `atlassian-check -config <config> refresh a_allowed` и затем `atlassian-check -config <config> inspect a_allowed`. `inspect` выводит время чтения объектов, результат `accessible-resources` и адресные проверки Jira `BROWSE_PROJECTS`. Для матрицы повтори `inspect` с ролями `a_denied`, `b`, `collector` и `owner`.

Для приращения используй по пять стендовых объектов. Проверь дату нижней границы и инвентарь в плане. На паузе после первой страницы обнови два последних объекта из показанного списка. Для Jira можно поменять summary через `PUT /rest/api/3/issue/{key}`, для Confluence - тело через `PUT /wiki/api/v2/pages/{id}` с увеличением версии, для GitLab - описание через `PUT /api/v4/projects/{id}/merge_requests/{iid}`. Дождись появления обеих правок в начале отдельной контрольной выдачи и продолжи Enter. Скрипт читает страницы и показывает `missing`, `extra` и `duplicates`. При `allow_drift` успешный результат означает, что эксперимент завершился и контрольный набор совпал с ожидаемым размером. Пропуски и повторы остаются в отчёте.

Сценарий выполняет все 57 проверок [параметризованного плана](mvp-09.example.json), повторяет два запроса после моделируемого отзыва доступа и проверяет окно создания workflow runs. Подменённый HTTP-открыватель передаёт синтетические статусы, JSON и заголовки штатному обработчику. Сеть и токены не нужны. В отчёте `simulation: true`. GitHub использует значение заголовка версии из плана, версии Jenkins и SonarQube в ответах обозначены `synthetic`.

| Источник | Допуск, отказ и ограниченный объект в модели | Кандидат по модели |
| --- | --- | --- |
| GitHub.com | Запрос уровня доступа даёт HTTP 200 с `read` для прямого и командного доступа и с `none` для пользователя без прав и пользователя второй организации. Закрытый для сборщика репозиторий даёт 404. Публичный репозиторий читается анонимно (200), уровень членства для постороннего — `none`. После отзыва доступ команды переходит из `read` в `none`, а чтение пользовательским токеном — из 200 в 404. | `service_account`, если стенд подтвердит чтение эффективных прав. Правила для публичных репозиториев проверяются отдельно. |
| Jenkins | Сборщик читает A/B (200), пользователь читает A (200) и получает 403 на B. Ограниченный job даёт 404 обоим. Запись о другом пользователе доступна (200) и содержит ID. | `user_token`, если стенд подтвердит привязку токена к пользователю и запрет после отзыва. |
| SonarQube | Сборщик читает A/B (200), пользователь читает A (200) и получает 403 на B. Ограниченный проект даёт 404 обоим. Запрос прав другого пользователя от сборщика даёт 403. | `user_token` при тех же условиях проверки на стенде. |

В прогоне все 24 запроса с бюджетом, включая два после отзыва, уложились в 2 с. Локальный таймер показал 0 мс после округления для каждого запроса. Это время обработки синтетических ответов в памяти. Для выбора режима сравнивать с бюджетом суммарное время реальных запросов.

- **GitHub.** Timeline, reviews, комментарии к ревью и обычные комментарии дали по 103 записи за 52 страницы по 2 записи (контрольный обход — 2 страницы по 100). В стабильных обходах PR и runs по 5 записей за 3 страницы. У двух попыток rerun разные наборы jobs, по 3 записи за 2 страницы на попытку. Список artifacts содержит живой и истёкший объекты. Запросы скачивания дали 302 и 410 соответственно. Основной лимит дал 403, `X-RateLimit-Remaining: 0` и заголовки квоты и сброса. Вторичный дал 429, `Retry-After: 60` и ненулевой остаток. Окно создания за день изменения исключило старый запуск после rerun и вернуло только новый.
- **Jenkins.** Стабильный обход `allBuilds` дал 5 сборок за 3 страницы диапазонами по 2. Исходный SHA и ветка доступны в синтетических `actions[].lastBuiltRevision.SHA1` и `actions[].lastBuiltRevision.branch[].name`. Ответ прокси при ограничении квоты предстоит снять на стенде.
- **SonarQube.** Стабильный поиск дал 5 issues за 3 страницы по 2. Отдельная фикстура с `total=10001` дала 500 записей на странице 20 при `ps=500` и 400 на странице 21. В списке анализов заполнен `revision`. Ветки вернули только `main`, список PR пуст, запросы issues по ветке и PR дали 404. Возможности редакции и лимиты прокси предстоит проверить на стенде.

### Стендовая проверка

Запросы и права ниже предназначены для повторения экспериментов на стендах. Записать фактические версии, дату, ответы и время, затем сверить наблюдаемые эффекты с моделью и определить режим через `Probe`.

### GitHub.com

- Сборщик пробует `GET /repos/{owner}/{repo}/collaborators/{login}/permission` с учётными данными чтения репозитория с доступом к Metadata, без прав администратора организации. Зафиксировать тип токена и выданные scopes. Сопоставить HTTP, `permission`, `role_name`, `user.login` и время для прямого участника, участника только через команду, пользователя без доступа, пользователя второй организации и репозитория, закрытого для сборщика. Сопоставить с `GET /user` и `GET /repos/{owner}/{repo}` от имени каждого пользователя. Для публичного репозитория проверить то же чтение без токена и отдельно запрос уровня доступа для пользователя без членства. После удаления тестового пользователя из команды повторять оба чтения с той же учётной записью до устойчивого запрета. Записать момент отзыва, время первого запрета и возможные последующие разрешения, затем восстановить членство.
- Для длинного PR собрать более 100 записей каждого вида и пройти ссылки `Link rel="next"`: `GET /repos/{owner}/{repo}/issues/{number}/timeline`, `/pulls/{number}/reviews`, `/pulls/{number}/comments` и `/issues/{number}/comments` с разрешением чтения Pull requests и, для issue endpoints, Issues или Pull requests. Записать число страниц, записей и сверку идентификаторов с перечнем фикстуры. Измеренный размер страницы указывается вместе с числом страниц.
- PR перечисляются через `GET /repos/{owner}/{repo}/pulls?state=all&sort=updated&direction=desc`. Снять полный контрольный набор, создать PR и изменить непрочитанный PR после первой страницы, сверить результат с повторным полным перечнём. Для runs запрос `GET /repos/{owner}/{repo}/actions/runs?created={range}` с Actions read ограничивает время **создания**. Скрипт сохраняет `created_at`, `updated_at`, `run_attempt` и SHA. Для приращений проверить rerun старого запуска, в том числе повторить чтение с окном, которое включает время изменения, но исключает время создания. Для полного контроля проверить отдельное окно создания старого запуска. При ограничении выдачи на 1000 результатов делить окно создания и сверять объединённые идентификаторы с перечнем.
- С Actions read проверить `GET /repos/{owner}/{repo}/actions/runs/{run_id}`, `/attempts/{attempt}` и `/attempts/{attempt}/jobs` для попыток 1 и 2 одного запуска. Сверить идентификаторы jobs по попыткам. `GET .../actions/runs/{run_id}/artifacts` сохраняет `expired` и `expires_at`. Для артефактов с известным ID сравнить HTTP у `GET /repos/{owner}/{repo}/actions/artifacts/{artifact_id}/zip` до и после истечения. Клиент фиксирует статус перенаправления без перехода по ссылке загрузки. Если запись исчезла из списка, всё равно проверить её по ранее сохранённому ID.
- На отдельном согласованном тестовом лимите снять `GET /rate_limit` до серии, затем по одному контрольному запросу `github_rate_primary` и `github_rate_secondary` при соответствующем ограничении. Сохраняются HTTP, `X-RateLimit-Limit`, `Remaining`, `Used`, `Reset`, `Resource` с префиксом `X-RateLimit-`, и `Retry-After`. Для 403/429 скрипт ищет сообщение о secondary rate limit. При его отсутствии и нулевом остатке отмечает основной лимит. Скрипт не расходует квоту серией запросов. Повторять запрос после `Retry-After` или сброса квоты. Если вторичный лимит получить не удалось, его поведение остаётся неподтверждённым.

### Jenkins

- Сверить заголовок `X-Jenkins` и установленный набор плагинов с [lock](../jenkins/plugins.txt) по данным оператора. Сборщик с `Overall/Read` и `Job/Read` на A/B пробует `GET /job/{job}/api/json?tree=name` для A, B и `cp90-control`. `GET /user/{login}/api/json?tree=id` проверяет доступность записи о другом пользователе. Само наличие записи не показывает его эффективное `Job/Read`. Сопоставить ответы с `GET /whoAmI/api/json` и теми же чтениями job от имени тестового пользователя только с A и пользователя второй организации только с B. Зафиксировать, есть ли в закреплённых плагинах читаемый способ получить эффективный допуск другого пользователя без прав на конфигурацию. Проверить существование ограниченного job отдельно через оператора.
- Запрос `GET /job/{job}/api/json?tree=allBuilds[number,timestamp,building,result]{start,end}` проверяет обход `allBuilds` диапазонами по 2 и по 100. Диапазоны начинаются с нуля, правая граница исключена. Сверять с полным перечнем номеров, известным оператору. На паузе поставить тестовую сборку в очередь, дождаться её появления в начале выдачи и продолжить. Для checkout Git в тестовой сборке запросить `GET /job/{job}/{number}/api/json?tree=number,actions[lastBuiltRevision[SHA1,branch[name,SHA1]]]`. Сверить SHA и ветку с известным checkout. Отдельно записать случай pipeline, где эти поля отсутствуют, и наличие параметров, нужных для привязки к коммиту.
- Указать наблюдаемые статус и заголовки при ограничении репозиторием или обратным прокси стенда, если владелец настроил тестовый лимит. В протоколе отличать лимит от ошибки авторизации и таймаута.

### SonarQube

- Сверить `GET /api/system/status` с записью стенда. Сборщик с `Browse` на A/B вызывает `GET /api/permissions/users?projectKey={project}&permission=user&selected=all&q={login}&p=1&ps=100` для заданного пользователя. При успешном ответе сверить точный логин и поле `selected`, затем проверить, учитывает ли ответ права через группы. Сравнить с `GET /api/users/current` и `GET /api/issues/search?components={project}&p=1&ps=1` с собственным токеном тестовых пользователей A/B и сборщика. В каждом случае измерить доступный проект, проект чужой организации и частный контроль `cp90-control`. Существование контрольного проекта подтверждает оператор.
- Для `GET /api/issues/search?components={project}&s=UPDATE_DATE&asc=false&p={page}&ps={size}` сравнить ключи и версии в полном обходе и после изменения двух непрочитанных issues. Проверить страницы 20 и 21 с `ps=500` на проекте с более чем 10 000 issues; записать HTTP, `paging.pageIndex`, `pageSize`, `total` и границу доступного диапазона. Если на стенде нет достаточно данных, результат для глубины остаётся открытым. Для анализов пройти `GET /api/project_analyses/search?project={project}&p={page}&ps={size}` и сравнить `analyses[].revision` с известными SHA тестовых анализов.
- Запросить `GET /api/project_branches/list?project={project}`, `GET /api/project_pull_requests/list?project={project}` и `GET /api/issues/search` с `branch` или `pullRequest`. Сравнить с основной веткой и с попыткой запустить тестовый анализ ветки и PR оператором. Пустой список без тестового анализа не доказывает отсутствие возможности в редакции.
- При настроенном тестовом лимите записать HTTP и заголовки ограничения отдельно от ошибки глубины выдачи и ошибки прав.

### Прогон MVP-09

Скопировать [план](mvp-09.example.json) в исключённую из Git папку `artifacts/`. Подставить URL, пользователей, репозитории, номера PR/сборки, IDs run/artifacts, окно создания и ключи проектов из фикстур. Для чтения A/B повторять матрицу с токеном каждого пользователя, меняя переменную `CP223_*_USER_*` и соответствующие поля плана. Токены брать на стенде. Для Jenkins значение `CP223_JENKINS*_BASIC` представляет собой Base64 от пары `login:api_token`. В JSON хранятся только имена переменных. Бюджет `budget_ms=2000` применяется к одному запросу, включая сетевую задержку и чтение JSON успешного ответа. Для режима из нескольких запросов отдельно измерить суммарное время.

```sh
python3 deploy/source-checks/source_checks.py artifacts/mvp-09.local.json --check github_permission_team
python3 deploy/source-checks/source_checks.py artifacts/mvp-09.local.json --check github_pulls_drift --interactive
python3 deploy/source-checks/source_checks.py artifacts/mvp-09.local.json --check jenkins_builds_drift --interactive
python3 deploy/source-checks/source_checks.py artifacts/mvp-09.local.json --check sonar_issues_drift --interactive
```

Выбирать остальные имена через повторяемый `--check`. Для сверки с полным стендовым инвентарём заполнить `expect_ids` и выставить `exact_inventory: true`. Отчёт покажет и отсутствующие, и лишние идентификаторы контрольного обхода. Если известен только размер инвентаря, заполнить `expected_count`. Для эксперимента с изменением использовать инвентарь после изменения и дождаться видимости правок перед Enter. Отчёт показывает `missing`, `extra`, `duplicates`, изменения контрольного набора и `stale_rows` для полей, выбранных в `observe_rows`. `complete` описывает завершение обхода средствами API. Сверка с независимым инвентарём нужна, поскольку оба обхода могут иметь один предел. `status: "observe"` оставляет HTTP-вердикт оператору, поэтому `matches` на таком запросе не подтверждает право. Для Jenkins и SonarQube при появлении ответа о лимите сохранить только статус, `Retry-After` и известные заголовки лимита прокси. В протокол внести обезличенные ответы, диапазоны времени и результаты сверки. Полные ответы и локальный план оставить на стенде.
