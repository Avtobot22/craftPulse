# Приёмка Jira Cloud и универсального импорта

Скрипты сверяют факты через API приложения и снимок PostgreSQL. Ожидаемые факты берутся из Jira Cloud REST API v3 или из отправленных файлов. Скрипты используют стандартную библиотеку Python 3.11 или новее.

## Стенд

Нужны выделенный тестовый проект Jira Cloud с назначаемым уровнем безопасности, старая открытая задача, выпуск craftPulse с worker и `adapter-jiracloud` из того же выпуска, учётные записи администратора и обычного пользователя, SOPS + age и `psql` с доступом только на чтение к базе ядра. Настрой подключение PostgreSQL через `PGSERVICE` и защищённый локальный файл паролей. Проверь, что эта база принадлежит указанному выпуску. Для чтения снимков подходит роль `craftpulse_backup`. SQL задаёт контекст организации на время транзакции и ограничивает выборку указанной организацией и источником.

Подготовь JSON-комплект SOPS с полями `jira_url`, `jira_token`, `jira_email`, `craftpulse_url` и `craftpulse_cookie`. Для проверки доступа добавь `viewer_cookie`. Cookie содержит пары `name=value` через точку с запятой. Укажи путь к зашифрованному комплекту через `BUNDLE`, а путь к ключу age передай SOPS через `SOPS_AGE_KEY_FILE`. Для каждого прогона используй новый закрытый каталог `OUT` вне Git. JSON-отчёты создаются с правами 0600. В журнал попадают время, операция, метод, HTTP-статус и длительность. Сырые ответы, заголовки и параметры запросов в журнал не пишутся.

Шаблон команд для выделенного проекта (`PROJECT_KEY` - ключ Jira, `PROJECT_ID` - UUID проекта craftPulse):

```sh
python3 deploy/tracker-acceptance/jira_fixtures.py --bundle "$BUNDLE" \
  --project "$PROJECT_KEY" --report "$OUT/prepare.json" prepare \
  --issue-type "$ISSUE_TYPE" --security-level "$SECURITY_LEVEL" \
  --old-key "$OLD_OPEN_KEY" --run-id "$RUN_ID"

python3 deploy/tracker-acceptance/jira_cloud.py --bundle "$BUNDLE" --sha "$RELEASE_SHA" \
  --organization "$ORG_ID" --project "$PROJECT_KEY" --history-from "$HISTORY_FROM" \
  --fixtures "$OUT/prepare.json" --run-id "$RUN_ID" --report "$OUT/jira.json"

python3 deploy/tracker-acceptance/universal_import.py --bundle "$BUNDLE" --sha "$RELEASE_SHA" \
  --organization "$ORG_ID" --project "$PROJECT_ID" --instance "$IMPORT_INSTANCE" \
  --task-key "$JIRA_FIXTURE_KEY" --jira-report "$OUT/jira.json" --report "$OUT/import.json"
```

`HISTORY_FROM` ставь раньше создания самой старой задачи проекта. Перед backfill скрипт повторно проверяет ID, статус и время изменения старой открытой задачи из отчёта подготовки. `JIRA_FIXTURE_KEY` возьми из `reconciliation[].actual` отчёта Jira. Сверка истории сравнивает ID, типы, время, поля, авторов и значения до и после изменения. Текстовые значения и идентификаторы учётных записей в отчёте хешируются. Для изменений описания, вложений и комментариев сверяются метаданные события. Для Jira сверяются статус и заголовок на дату по событиям и по сохранённой версии задачи. Для импорта сверяются ключ, заголовок, тип и статус версии на дату. Запусти подготовку и сверку второй раз на другом выделенном проекте или после восстановления начального снимка, с новым `RUN_ID` и `IMPORT_INSTANCE`. Сравни итоги по фазам, число и содержание фактов относительно входов каждого прогона. Сохрани оба набора отчётов с артефактами выпуска. UUID подключений, UUID квитанций и время запросов генерируются заново. Отчёт Jira сохраняет статус каждого раунда. После изменения и повтора скрипт ждёт новой попытки сбора и завершённой сверки с новым watermark. Снимок после повтора проверяется до ручного запуска сверки. Отчёт импорта сверяет номера, исходные ключи, типы, исходы и коды причин в журнале квитанций. У квитанций повторных пакетов и неподдержанной схемы журнал должен быть пуст.

Подкоманда `jira_fixtures.py inventory` только читает Jira Cloud. Чтобы задать дату снимка, укажи `--as-of` перед именем подкоманды. При ответе Jira 429 скрипт ждёт по `Retry-After`. На запрос отводится до трёх повторов и до 120 секунд суммарного ожидания. Каждая попытка попадает в отчёт. Сквозной прогон использует провайдер `jira_cloud` из [текущего выпуска профиля D](../profile-d/jira-cloud.md).

## Доступ, расписание и токен

Общие параметры `observe.py --bundle "$BUNDLE" --sha "$RELEASE_SHA" --report "$OUT/имя.json"` указываются перед подкомандой.

- `revocation --task "$TASK_ID" --control-task "$CONTROL_TASK_ID" --source-account "$ACCOUNT_ID" --person "$PERSON_ID"`. До запуска убедись, что у тестового пользователя есть действующая пользовательская OAuth-сессия Jira в craftPulse и он видит тестовую задачу. Когда скрипт начнёт опрос, отзови Browse Projects тестового пользователя в Jira. Контрольная задача должна принадлежать независимой области, которую пользователь продолжает читать. Измерение начинается перед действием оператора и включает его задержку. Восстанови право перед следующим прогоном.
- `adapter-unavailable` принимает те же параметры. После начала опроса останови выделенный адаптер Jira. Используй контрольную задачу источника, который останется доступен. При повторной привязке укажи текущий `--base-assignment`. После проверки запусти адаптер.
- `daily --connection "$CONNECTION_ID" --baseline "$OUT/jira.json"`. После сверки Jira оставь выделенное подключение активным, исключи ручные запуски и webhook. Обнови сессию в SOPS и запусти наблюдение до истечения 23 часов от сохранённого `last_attempt_at`. Отчёт показывает интервал до первой замеченной отметки попытки, новый watermark и длительность завершившейся сверки задач. `getSyncStatus` обновляет `last_attempt_at` после запроса каждой страницы. Отметка в пределах 24 часов подтверждает, что сбор успел начаться. Интервал от замеченной страницы до конца сверки даёт нижнюю границу длительности сбора. Для точного замера начала и длительности сохрани журнал запросов стенда.
- `credentials --connection "$CONNECTION_ID" --victorialogs "$LOG_EXPORT" --core-dump "$CORE_DUMP"`. Передай непустые несжатые выгрузки в UTF-8. Выгрузи логи за весь прогон в JSON Lines через `/select/logsql/query` с `unpack_json`. Для базы ядра используй текстовую выгрузку. Получай выгрузки на стороне стенда в закрытом каталоге. Для запроса логов используй [инструкцию профиля D](../profile-d/observability/README.md). В отчёт попадут размеры просмотренных выгрузок. Храни с отчётами только обезличенные журналы.

Оба сценария доступа требуют, чтобы обычный пользователь до отказа вошёл в craftPulse, подключил свою учётную запись Jira через OAuth и видел тестовую задачу. В текущем Jira Cloud адаптер возвращает `jira_access_revocation_unverified` даже при успешном чтении Jira, и ядро закрывает выдачу. Для стендового замера нужен выпуск с проверяемым разрешением на просмотр. Автоматические тесты воспроизводят переход от разрешения к отказу, закрытие области при неопределённом ответе и ответ `getTask` с HTTP 404 после остановки тестового адаптера и истечения 60 секунд.

## Тестовая среда

Штатные тесты приложения поднимают PostgreSQL и SeaweedFS через Docker. Запусти из корня репозитория:

```sh
python3 deploy/tracker-acceptance/test_environment.py --report "$OUT/test-environment.json"
```

Скрипт сохраняет SHA рабочей базы и исход каждого выбранного сценария. Пропуск теста или подтеста считается ошибкой. Сырые логи Go в отчёт не попадают. Для диагностики отдельного сценария запусти его через `timeout -k 2s 90s go test -p=2 ./internal/app -parallel=2 -count=1 -run '^ИмяТеста$'` из `backend/`. Отчёт относится к тестовому окружению.

На профиле D запрос больше 25 MiB может отклонить nginx. В этом случае отчёт импорта фиксирует HTTP 413 и повторную сверку принятых фактов.

Эти тесты воспроизводят отказы чтения и сверки, отбрасывание недопустимых пакетов, прерывание транзакции обработки пакета и сравнение журнала после повтора.

Для замера NFR-09 останови worker после начала обработки и до фиксации пакета. Сохрани UTC-отметку начала обработки этой квитанции (`STARTED_AT`, по журналу стенда или `attempted_at` задания `ingest.package` в состоянии `running`) и UTC-время остановки (`STOPPED_AT`). Выполни контрольный и прерванный прогоны с одним JSON-пакетом `tasks/1`, в одном проекте craftPulse и с разными новыми ключами экземпляров импорта. Укажи `AS_OF` в диапазоне дат пакета. Пока worker остановлен, запусти:

```sh
python3 deploy/tracker-acceptance/observe.py --bundle "$BUNDLE" --sha "$RELEASE_SHA" \
  --report "$OUT/recovery.json" recover-import --organization "$ORG_ID" --project "$PROJECT_ID" \
  --control-instance "$CONTROL_INSTANCE" --interrupted-instance "$INTERRUPTED_INSTANCE" \
  --control-receipt "$CONTROL_RECEIPT" --interrupted-receipt "$INTERRUPTED_RECEIPT" \
  --started-at "$STARTED_AT" --stopped-at "$STOPPED_AT" --as-of "$AS_OF"
```

Когда скрипт попросит, запусти worker. Отчёт содержит время до терминального состояния квитанции, журналы её записей и сверку нормализованных фактов обоих прогонов. Порог в пять минут измеряется от остановки до завершения сверки.

Задача CI `tracker-acceptance` запускает тесты скриптов при изменении этого каталога или workflow `Repository`. Результат учитывает обязательная проверка `ci`. Для локального запуска из корня выполни:

```sh
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s deploy/tracker-acceptance -v
```
