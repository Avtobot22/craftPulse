# Jira Cloud на стенде

Профиль D добавляет отдельный контейнер `adapter-jiracloud` из OCI-выпуска
`craftpulse-adapter-jiracloud`. Имя провайдера в ядре - `jira_cloud`.

## Переход действующего стенда

[Стенд после переноса](../stand/README.md) запускает приложение в Compose-проекте
`craftpulse-product`. Для перехода на профиль D используй его PostgreSQL и
SeaweedFS. Запланируй окно обслуживания и сделай проверенную резервную копию.

1. Узнай имена томов, смонтированных в `/var/lib/postgresql` и `/data` у
   действующих контейнеров PostgreSQL и SeaweedFS, через `docker inspect`.
   После восстановления снимка имена могут отличаться. В `rollout.json`
   задай эти имена в `stand_data_volumes.postgres` и `stand_data_volumes.objects`.
   Compose подключит существующие тома как внешние. Следующие выкаты проверят,
   что имена совпадают с активным выпуском.
2. Перенеси действующие пароли PostgreSQL, ключ бакета и мастер-ключ ядра в
   комплект SOPS на машине оператора. В `rollout.json` и комплекте сохрани
   параметры и секреты OIDC обеих организаций `org-a` и `org-b`.
   Подготовь профиль D по [общей инструкции](README.md#подготовка-к-первому-выкату).
3. Останови все сервисы старого проекта приложения командой `docker compose stop`
   из `/opt/craftpulse/product` с действующей конфигурацией. Одновременно
   открывать эти тома из двух проектов нельзя.
4. В [конфигурации Caddy](../stand/Caddyfile) сохрани обработчики Atlassian
   и запрет `/control/*`. Удали матчинг `@backend` и его обработчик. Направь
   общий обработчик на HTTPS-порт nginx профиля D, по умолчанию 18443.
   При установленной в nginx публично доверенной цепочке для
   `craftpulse.defects.team` используй этот блок.

   ```caddy
   handle {
       reverse_proxy https://127.0.0.1:18443 {
           header_up Host {http.request.host}
           transport http {
               tls_server_name craftpulse.defects.team
           }
       }
   }
   ```

   Проверь конфигурацию через `caddy validate`, выполни reload и запусти
   первый выкат по шагам ниже. Протокол установки проверит приложение
   по публичному адресу.

При неудачном первом переходе останови сервисы профиля D по сохранённому
`compose.json` последней попытки в `releases/` и верни прежнюю маршрутизацию Caddy.
Если выкат уже повысил версию схемы, проверь совместимость старого выпуска или
восстанови резервную копию перед запуском старого проекта. После первого
успешного выката для возврата между выпусками профиля D используй `rollback`.

## Добавление адаптера

1. Подготовь [профиль D](README.md) и убедись, что манифест выбранного выпуска
   содержит digest `craftpulse-adapter-jiracloud` и версию его схемы.
2. На машине оператора в комплекте SOPS + age добавь `adapters.jiracloud`
   с полями `owner_password`, `app_password`, `master_key` и `service_key`.
   Сгенерируй независимые случайные значения. Мастер-ключ - 32 байта в Base64.
   Укажи `adapter_ca_cert` и `adapter_ca_key` внутреннего центра установки.
3. Используй [настройки сетей стенда](rollout.example.json).
   Добавь `jiracloud` в `required_adapters`, чтобы выкат требовал его
   присутствия в манифесте и комплекте секретов.
   Jira Cloud находится в Atlassian Cloud по адресу
   `https://craftpulse-mvp.atlassian.net`. Адаптеру нужен исходящий HTTPS
   в публичную сеть. Его `SOURCE_PRIVATE_NETWORKS` пуст, сеть установки
   `172.31.84.0/27` запрещена для подключений к источникам. Порты адаптера
   доступны внутри Compose, публикации на хосте нет.
4. Выполни `python3 deploy/profile-d/rollout.py deploy <SHA>` на машине оператора.
   Выкат создаст базу `adapter_jiracloud`. Роль `adapter_jiracloud_owner`
   выполнит `migrate`, runtime-роль `adapter_jiracloud` получит только
   необходимые права чтения и записи. Compose задаст лимит памяти и swap 48 MiB
   и `GOMEMLIMIT=36MiB`. Проба контейнера проверит `/livez`, гейт выката по TLS
   сверит `/version` и дождётся `/readyz`. Протокол установки запишет
   `jira_cloud contract <версия>`.
5. Настрой тестовое подключение Jira Cloud в ядре и запусти сбор. Храни
   учётные данные Jira в хранилище адаптера. На хосте ключи адаптера
   остаются в файлах процессов с режимом `0400` внутри закрытых снимков
   выката. Ключ центра и ключ age остаются у оператора.

## Ротация служебного ключа и сертификата

Меняй поля `adapters.jiracloud` через SOPS. После каждого шага выкати текущий
SHA. При смене ключа ядро использует только `service_key`, а адаптер принимает
оба значения, пока указан `previous_service_key`.

1. Оставь действующий `service_key` и запиши новый ключ в `previous_service_key`.
   После выката адаптер принимает оба значения, а ядро продолжает работать
   с действующим ключом.
2. Поменяй значения местами и повтори выкат. Проверь вызов по тестовому
   подключению с новым ключом.
3. Удали `previous_service_key` и повтори выкат, чтобы отозвать прежний ключ.

Для возврата образа из выпуска с прежним ключом используй `deploy <прежний-SHA>`
с актуальным комплектом секретов. `rollback` проверяет, что снимок использует
действующий ключ и не возвращает отозванный.

Для перевыпуска сертификата повтори выкат с прежним центром установки.
Операторская команда создаст новый сертификат на 365 дней с SAN
`adapter-jiracloud`. Новый сертификат начинает действовать после пересоздания
контейнера. Проверь остаток срока на дашборде сбора.

## Ротация мастер-ключа

Выполняй ротацию в окно обслуживания. На хосте захвати `flock` файла `lock` в
каталоге состояния rollout на всё время работы и убедись, что `pending` в
`state.json` пуст. Закрой доступ на запись и останови `api`, `worker` и
`adapter-jiracloud`. Подготовь проверенную зашифрованную копию базы адаптера
и сохрани старый ключ в зашифрованном архиве для восстановления этой копии.

1. На машине оператора сгенерируй новый ключ в SOPS. Передай его на хост
   прямо в подготовленный файл процесса с владельцем UID/GID 65532 и
   режимом `0400`. Держи файл рядом с `master-key` в закрытом каталоге
   секретов активного снимка. В аргументах и переменных используй только пути
   и номера версий.
2. По `state.json` найди `compose.json` активного снимка. Выполни его
   `adapter-jiracloud-migrate` один раз под владельцем. В примере `$compose` -
   абсолютный путь к найденному `compose.json`, `$next_key` - путь к файлу
   нового ключа, `$old_version` - текущая версия из конфигурации сервиса,
   `$new_version` - следующий номер.

   ```sh
   docker compose --env-file /dev/null -f "$compose" run --rm --no-deps -T \
     -v "$next_key:/run/secrets/master-key-next:ro" \
     -e ADAPTER_MASTER_KEY_FILE=/run/secrets/master-key-next \
     -e ADAPTER_MASTER_KEY_VERSION="$new_version" \
     -e ADAPTER_PREVIOUS_MASTER_KEY_FILE=/run/secrets/master-key \
     -e ADAPTER_PREVIOUS_MASTER_KEY_VERSION="$old_version" \
     adapter-jiracloud-migrate
   ```

   Под владельцем базы проверь, что `SELECT DISTINCT master_key_version FROM adapter.org_key`
   возвращает только новый номер либо пустой набор. Если команда прервалась,
   сверяй версию в БД перед запуском сервисов. После подтверждённого перехода
   на новый ключ завершай замену файлов и конфигурации. Чтобы вернуть старый
   ключ, сначала выполни `migrate` с обратной парой ключей и версий.
3. Атомарно замени `master-key` активного снимка новым файлом. В активном
   `compose.json` выставь новый `ADAPTER_MASTER_KEY_VERSION` для
   `adapter-jiracloud` и `adapter-jiracloud-migrate`.
   В `rollout.json` установи тот же номер в `adapter_master_key_versions.jiracloud`.
   Оставь в SOPS новый ключ в поле `adapters.jiracloud.master_key`.
4. Пересоздай остановленные процессы из активного `compose.json`.
   Проверь сбор и проверку прав, затем освободи блокировку и повтори
   `deploy <SHA>` с актуальным комплектом для проверки установки.
   Снимки со старым ключом не подходят для обычного `rollback`.
   Для возврата такого образа используй `deploy <прежний-SHA>` с актуальным
   комплектом и версией ключа.

## Приёмка выпуска

- Проверь `/version` и `/readyz` по HTTPS внутри сети Compose с CA установки.
  Сверь SHA, контракт и запись в протоколе установки.
- На изолированной копии стенда подмени сертификат на сертификат другого
  центра и проверь отказ вызова от ядра. Для проверки алерта установи
  доверенный сертификат с запасом 20 дней и дождись `Firing`.
- После успешного сбора останови сбор тестового подключения и проверь алерт
  после 26 часов от последнего успеха. Отзови токен тестового подключения и
  запусти сбор для проверки алерта 401/403. Восстанови токен и TLS обычным выкатом.
- При выгрузке проекта CPA или CPB сними `memory.peak` и `memory.events` cgroup
  контейнера. Сверь пиковую память с 48 MiB и убедись, что счётчик OOM не вырос.
- Выполни `rollback <прежний-SHA>` для ранее развёрнутого выпуска с адаптером.
  Сверь digest контейнера, SHA, контракт и готовность.
