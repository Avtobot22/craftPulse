# Браузерная приёмка AC-01

Подготовь выделенную установку с тестовым GitLab по [инструкции AC-01](ac01.md).
Нужны `org-a` и `org-b`, четыре тестовые учётные записи и снимок базы после
`api install`. Сохрани снимок до первого входа администраторов. `org-b` должна
оставаться в `setup` до сценария 05. Для API-приёмки используй отдельное
восстановление того же снимка.

Выкати опубликованный выпуск по [инструкции профиля D](../profile-d/README.md#выкат)
и сверь `commit_sha` из `/version` с SHA выпуска:

```sh
python3 deploy/profile-d/rollout.py deploy --bundle /secure/stand.sops.json "$AC01_RELEASE_SHA"
```

Тесты создают команду и проект с именами из API-приёмки, связывают их,
назначают роли тестовым пользователям и сохраняют правки структуры. Перед
каждым прогоном останови API и worker, восстанови снимок и запусти тот же
выпуск. Используй один запуск за раз.

## Матрица окружения

Используй Node.js и npm по основной инструкции. Установи тестовый пакет и
сборки браузеров, закреплённые Playwright 1.65.0:

```sh
npm --prefix frontend/e2e install --package-lock=false --ignore-scripts --no-audit --no-fund
cd frontend/e2e
npm exec --no -- playwright install chromium firefox
cd ../..
```

На дату заморозки приёмки зафиксируй версию и выпуск ОС машины оператора,
полные версии комплектных Chromium и Firefox по выводу команды ниже.
Одна версия каждого браузера используется для обеих ширин. Масштаб 100%.
`run.json` содержит фактическую версию браузера, ОС и размер окна.

```sh
node --input-type=module -e 'import os from "node:os"; console.log(os.platform(), os.release(), os.version())'
(cd frontend/e2e && node --input-type=module -e '
  import { chromium, firefox } from "@playwright/test";
  for (const engine of [chromium, firefox]) {
    const browser = await engine.launch();
    console.log(engine.name(), browser.version());
    await browser.close();
  }
')
```

| `AC01_PROFILE` | Браузер | Окно в CSS px |
| --- | --- | --- |
| `chromium-1280` | Chromium | 1280 × 800 |
| `chromium-1920` | Chromium | 1920 × 1080 |
| `firefox-1280` | Firefox | 1280 × 800 |
| `firefox-1920` | Firefox | 1920 × 1080 |

## Два прогона

Задай в окружении оператора:

- `AC01_SITE` и `AC01_GITLAB` - HTTPS-адреса приложения и GitLab без пути.
- `AC01_RELEASE_SHA` - полный SHA опубликованного выпуска.
- `AC01_PROFILE` - строка из матрицы. `AC01_BROWSER_VERSION` - зафиксированная версия выбранного браузера.
- `AC01_EVIDENCE_DIR` - новый абсолютный каталог вне checkout с правами 0700.
- `AC01_ADMIN_A_PASSWORD`, `AC01_ADMIN_B_PASSWORD`, `AC01_MEMBER_PASSWORD` и
  `AC01_OUTSIDER_PASSWORD` - пароли `cp87-admin-a`, `cp87-admin-b`, `cp87-member` и
  `cp87-no-repo` из журнала GitLab. Вводи их через менеджер секретов или
  скрытый ввод в терминале. Отключи отладочные логи Playwright и запись сеанса терминала.
- `AC01_FOREIGN_MARKERS` - JSON-массив точных строк с уникальными числами или
  подписями объектов второй организации из набора показа, если в нём есть
  числовые данные. Имена и ID команды и проекта тест получает со стенда.

Для каждой строки матрицы восстанови снимок, выполни команду, затем повтори
с тем же выпуском и пустым каталогом записи. Выполняй все семь сценариев
одной командой. Проверка первого входа (05) идёт до чтения структуры `org-b`
в сценарии 03:

```sh
npm --prefix frontend/e2e test
```

| Сценарий | Результат |
| --- | --- |
| 01 | Вход через GitLab и выбор команды и проекта только первой организации |
| 02 | После выхода старая вкладка показывает UI-03 и убирает данные организации |
| 03 | Прямые ссылки на проект и команду второй организации открывают UI-04 без данных этих объектов в DOM |
| 04 | После `endUserSessions` запрос формы получает `401 auth_required`. Повторный вход возвращает на прежний URL, сохранения формы нет |
| 05 | Посторонняя учётная запись получает отказ, заявленный администратор открывает UI-06 и переходит к UI-07 |
| 06 | Два администратора открывают одну версию UI-07. Второй получает UI-17, видит сохранённое изменение первого и явно подтверждает своё. Уход с новым черновиком показывает UI-18 |
| 07 | Назначенная в UI-08 область появляется у участника со следующего запроса в той же сессии |

Для ручной проверки после входа вставь `/organization/structure` в адресную
строку и убедись, что открылся UI-07. Автоматический сценарий 06 тоже открывает
этот URL новым запросом к стенду и проверяет HTML и загрузку редактора.

## Свидетельства

В `run.json` записываются итоги всех семи сценариев. При ошибке репортёр
Playwright пишет отдельную JSON-трассу упавших именованных шагов, с названиями
шагов, временем начала и длительностью. Для защиты OAuth-данных отключены
стандартный trace ZIP, скриншоты и видео. Репортёр берёт данные из событий
теста и исключает ошибки с подстановкой значений, сетевой обмен и содержимое DOM.

В ручной проверке возьми значение `__Host-cp_session` из текущей браузерной
сессии, передай его скрытым вводом в окружение как `AC01_OBSERVED_SESSION` и выполни
для каталога каждого прогона:

```sh
node frontend/e2e/verify-evidence.mjs
unset AC01_OBSERVED_SESSION
```

Сканер ищет пароли и значение cookie в записях, трассах и файлах checkout,
которые Git видит для публикации. Он также сверяет SHA-256 трасс с записью
прогона и печатает SHA-256 файла `run.json`. После успешной проверки сохрани
записи и трассы во внешнем хранилище
свидетельств. В репозитории зафиксируй только адреса и SHA-256 файлов.
