# Шаг 0. Восстановление стенда перед показом

[Manifest](../manifest.json) содержит записи шести источников и GitLab Runner,
права учётных записей, версии источников, список активных плагинов Jenkins и
закреплённую версию GitHub REST API. В разделе `craftpulse` указаны SHA, версии
схем и digest образов выпуска. Раздел `runtime_images` фиксирует образы,
которые были запущены на стенде.

Стенд использует Jira Cloud и Confluence Cloud из [#88](https://github.com/Avtobot22/craftPulse/issues/88).
Confluence сообщает текущую сборку через `commitHash`. Время жизни этой записи
определяет обновление SaaS. При расхождении выясни причину и обнови запись
экземпляра в `sources.json` после проверки нового ответа.

## Подготовка

Команды снятия и восстановления рассчитаны на Linux-хост стенда из
[инструкции по развёртыванию](../README.md). Нужны Python 3.11+, Docker Compose,
GNU tar и age. Для SeaweedFS скрипт использует закреплённый образ AWS CLI
в сетевом пространстве контейнера SeaweedFS. Бакет `craftpulse` должен
автоматически создаваться при запуске SeaweedFS.

Подготовь каталог для снимка вне checkout, запись выпуска и закрытый комплект
стенда. Файлы конфигурации Compose, HTTPS-маршруты, ключ расшифровки age и
комплект `/etc/craftpulse-product` хранятся у оператора. Комплект продукта должен
соответствовать снимку, в том числе master key, OIDC и параметры SeaweedFS.
Для базы адаптера `adapter_git` скрипт ожидает файлы `adapter_git-password` и
`adapter_git-owner-password` по тому же пути. Остальные имена образуются так же.
Учётные данные источников передавай в окружении процесса через хранилище секретов.

| Переменная | Доступ |
| --- | --- |
| `CP92_ATLASSIAN_BASIC` | Base64 от `email:token` оператора тестового сайта. Чтение и изменение объектов CPA, CPB, CPZ, ORGA и ORGB |
| `CP92_GITLAB_TOKEN` | PAT оператора с `read_api` для проверки шести тестовых проектов и менеджеров runner #1. Токен должен действовать после восстановления GitLab |
| `CP92_JENKINS_BASIC` | Base64 от `login:token` оператора Jenkins с доступом к плагинам и контрольным jobs |
| `CP92_SONAR_TOKEN` | Токен пользователя с доступом к истории анализов всех трёх контрольных проектов SonarQube |
| `GITHUB_RESET_TOKEN` | Доступ оператора для процедуры [сброса #89](../../github/manage.py). При отсутствии переменной используется авторизация `gh` этого пользователя |

`verify --local` обращается к Caddy на 127.0.0.1 с исходным именем хоста и проверкой
сертификата. Для проверки с другой машины используй `verify` без `--local`.
Снятие и восстановление используют локальный Caddy.

## Снятие начального снимка

На хосте стенда, из checkout с инструментом и с правами доступа к Docker и
файлам состояния, выполни команды ниже. На время операции приостанови изменения
тестовых источников. Дождись завершения выполняющихся pipeline и jobs.

```sh
python3 deploy/stand/snapshot/stand_snapshot.py manifest \
  --release /opt/craftpulse/product/release-manifest.json \
  --output /var/backups/craftpulse/stand-manifest.json

python3 deploy/stand/snapshot/stand_snapshot.py verify --local \
  --manifest /var/backups/craftpulse/stand-manifest.json

python3 deploy/stand/snapshot/stand_snapshot.py capture \
  --manifest /var/backups/craftpulse/stand-manifest.json \
  --snapshot /var/backups/craftpulse/initial \
  --recipient "$BACKUP_AGE_RECIPIENT"
```

Скрипт сверяет запущенные образы с manifest, приостанавливает запись продукта,
снимает роли без паролей и архивы ядра и баз адаптеров под `craftpulse_backup`
с включённым RLS. В снимок входят объекты SeaweedFS и список ключей с SHA-256.
GitLab копируется штатным `gitlab-backup` вместе с конфигурацией и состоянием
runner. Тома Jenkins, SonarQube и его PostgreSQL копируются после остановки
сервисов с сохранением числовых UID/GID. Состояние GitHub и Atlassian записывается
через API. Архивы и списки объектов шифруются age. В открытом виде остаются
manifest, счётчики строк и контрольные суммы.

Сохрани снимок вне хоста и отдельно запиши напечатанный `checkpoint_sha256`.
Каталог снимка появляется только после успешного снятия и сверки.

## Восстановление, сверка и вход

1. На выделенном стенде с теми же путями и конфигурацией Compose останови
   изменения тестовых источников. Подготовь доступ к расшифровке и запусти:

   ```sh
   python3 deploy/stand/snapshot/stand_snapshot.py restore \
     --snapshot /var/backups/craftpulse/initial \
     --checkpoint-sha256 "$CHECKPOINT_SHA256" \
     --identity /secure/craftpulse-backup.agekey \
     --apply
   ```

   Переход на сохранённые образы идёт по digest. Скрипт проверяет целостность
   архива, затем поднимает PostgreSQL и SeaweedFS на свежих томах, восстанавливает
   роли, базы и ключи бакета и сверяет их с контрольной точкой. Старые тома
   сохраняются. GitLab восстанавливается штатной командой в новом каталоге
   данных, Jenkins и SonarQube - из архива томов. Docker Compose использует
   созданные скриптом `compose.override.yaml`. При последующих ручных вызовах
   Compose используй оба файла или запускай его из каталога установки без `-f`.

2. Проверь последнюю JSON-строку команды. Поле `seconds` содержит длительность,
   `rows` - результаты сверки таблиц, `objects` - число сверенных ключей и хэшей.
   Скрипт также сверяет состояние источников и версии. Для отдельной проверки
   повтори команду с manifest из снимка:

   ```sh
   python3 deploy/stand/snapshot/stand_snapshot.py verify --local \
     --manifest /var/backups/craftpulse/initial/manifest.json
   ```

3. Открой [craftPulse](https://craftpulse.defects.team), войди через GitLab обеими
   учётными записями администратора и проверь организации `org-a` и `org-b`.

## Прогон с изменениями

Для контрольного прогона измени строки продукта и объект в бакете, создай
ветку и тестовый MR в GitLab, выполни тестовую сборку Jenkins и анализ SonarQube.
В Atlassian измени заголовок или содержимое тестовой задачи и страницы. Новым
объектам дай заголовок с префиксом `cp92-reset-`. Сброс Atlassian проверяет ID
проектов и пространств, возвращает заголовки, описания и метки Jira, заголовки
и содержимое страниц Confluence и удаляет помеченные новые объекты.
Изменение статуса, уровня безопасности или родителя, удаление оригинала и новый
объект без префикса останавливают сброс. Историю SaaS и настройки доступа этот
сброс не воспроизводит.

Для GitHub меняй существующие ветки и reviewer requests или добавь комментарий
от `craftpulse-mvp-bot[bot]`. Скрипт GitHub проверяет чистоту состояния трёх
репозиториев после применения. Новый или слитый PR и изменения вне разрешённых
операций требуют отдельного восстановления по процедуре #89.

После восстановления сохрани JSON-вывод с длительностью и результатами сверок.
Скопируй manifest, поменяй `sources.jira.version` в копии и запусти `verify` с
ней. Команда должна завершиться с ошибкой и указать расхождение `jira: differs at version`.
