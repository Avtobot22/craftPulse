# Работа над craftPulse

Задачи, обсуждение изменений и ревью ведём в GitHub. Спецификации продукта храним в `docs/` и меняем вместе с реализацией.

## От задачи до слияния

1. Создай Issue по шаблону задачи или ошибки. Укажи результат, критерии приёмки и способ проверки.
2. Выбери одну основную `area:*`, приоритет и исполнителя. Для новой возможности замени `type:task` на `type:feature`.
3. Добавь задачу на доску. До начала работы проверь родителя и блокирующие зависимости.
4. Создай короткую ветку от актуальной `main`: `feat/123-role-dashboard`, `fix/124-http-timeout` или `docs/125-metrics`.
5. Открой draft PR, если хочешь показать работу заранее. В описании свяжи его с Issue и запиши результаты проверок.
6. Когда изменение готово, переведи draft PR в Ready for review. При необходимости пригласи участника на необязательное ревью.
7. После зелёных проверок выполни squash merge. Автор отвечает за готовность изменения; чужое одобрение не требуется. Рабочая ветка удалится автоматически.

Для опечатки или небольшой служебной правки отдельная Issue необязательна. PR и проверки обязательны для всех изменений.

```sh
git switch main
git pull --ff-only
git switch -c feat/123-role-dashboard
```

## Размер задачи и готовность к работе

Одна задача описывает результат, который можно проверить отдельно. Она готова к работе, когда понятны границы, критерии приёмки, проверка и зависимости. Если задачу нельзя закончить за несколько рабочих дней, сначала раздели её.

Крупные результаты оформляй как Issue с `type:epic`; отдельные части добавляй через Sub-issues. У каждой дочерней задачи свой исполнитель и направление. Родительская связь не заменяет блокирующую зависимость: её создавай через Relationships → Blocked by / Blocking. Не связывай все задачи между собой без причины.

Story Points и спринты не обязательны. Оценки не переводим в часы и не используем для сравнения участников. Основной способ планирования - порядок готовых задач и ограничение незавершённой работы: одна активная задача на человека, следующая берётся после завершения или явной блокировки текущей.

## Ветки, PR и коммиты

Постоянная рабочая ветка - `main`. Отдельную интеграционную ветку заводим только при появлении конкретной необходимости. `main` содержит проверенные изменения; выпуск продукта отмечается отдельным тегом и GitHub Release.

Заголовок PR использует Conventional Commits и становится единственной строкой squash-коммита:

```text
feat(frontend): добавить ролевой дашборд
fix(backend): завершать запрос по таймауту
docs: уточнить расчёт метрики
ci: обновить проверки репозитория
```

Разрешены `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`; scope необязателен. Несовместимое изменение отмечай `!` перед двоеточием и объясняй в PR. Заголовок - одна строка до 100 символов. В сообщения коммитов и PR не добавляй подписи инструментов и соавторства ИИ.

Имя ветки использует те же типы: `feat/123-role-dashboard`, `fix/124-http-timeout`, `refactor/126-metric-calculation`, `test/127-input-validation`, `ci/128-repository-checks`. Пиши короткое описание строчной латиницей, слова разделяй дефисами; номер Issue добавляй при её наличии. Для мелкой служебной работы допустимо `chore/update-tooling`. Длина имени - до 100 символов. Для автоматических PR Dependabot разрешены его штатные имена `dependabot/*`; обычный автор использовать это исключение не может.

CI проверяет имя ветки, заголовок PR и заголовок каждого нового коммита в PR. Рабочие коммиты также называй `type(scope): описание`: `WIP`, `fix stuff` и заголовки без типа проверку не пройдут. Унаследованную историю до ответвления от `main` переименовывать не требуется. Если уже отправленный коммит нужно переименовать, согласуй изменение общей рабочей ветки; не переписывай чужую работу.

Для облачного агента предусмотрены штатные ветки `copilot/short-description` и пустой служебный коммит `Initial plan`. CI допускает такой коммит только при полном отсутствии изменений файлов относительно первого родителя. Рабочие коммиты с изменениями, заголовок PR и итоговый squash-коммит подчиняются обычным правилам. Инструкции агента находятся в `.github/copilot-instructions.md`.

Чтобы неверный заголовок отклонялся ещё до создания локального коммита, после клонирования подключи общий hook:

```sh
git config --local core.hooksPath .githooks
```

Настройка локальна для checkout и выполняется отдельно в каждом клоне. Обязательный CI работает независимо от локальных hooks.

В PR пиши `Closes #123`, только если он полностью завершает задачу. Для части работы используй `Refs #123`. Эпик закрывается после завершения дочерних задач и проверки общего результата. Автозакрытие Issue при merge работает для PR в основную ветку.

## Проверка и ревью

Перед ревью проверь diff, запусти команды из README и укажи их результат в PR. Для изменения продукта добавь проверки затронутого поведения; для UI приложи изображение или запись. Для ошибки сначала воспроизведи её и проверь, что исправление устраняет причину. Незапущенные проверки называй явно.

`repository-check` проверяет имя ветки, заголовки PR и новых коммитов, локальные ссылки на файлы в Markdown, JSON, нежелательные файлы и тесты инструментов репозитория. Сетевые URL, Markdown reference links и фрагменты `#anchor` он не проверяет. Это не проверка корректности приложения. При появлении кода его typecheck, lint, тесты и build нужно включить в этот обязательный job либо в зависящий от них итоговый job с тем же именем.

Для слияния нужны успешный `repository-check` и актуальность относительно `main`. Обязательного одобрения другого участника и отдельного запрета на слияние при незакрытых обсуждениях нет. Автор отвечает за проверку критериев задачи, учёт замечаний и готовность изменения. CODEOWNERS по умолчанию запрашивает владельца репозитория на необязательное ревью. Ответственных за отдельные каталоги назначаем по фактическому распределению работы.

Прямые push, force push и удаление `main` запрещены правилами репозитория, включая администратора. Смена самих правил остаётся административным действием; не используй её как способ пропустить CI. Не делай force push в чужие рабочие ветки. Для исправления в `main` создай отдельный PR, в том числе для revert.

## Документы и секреты

Продуктовые документы описывают текущее поведение без истории обсуждений и служебных отчётов. Персональные окружения, ключи, реальные `.env`, записи встреч и подключённая папка `shared/` в этот репозиторий не попадают. Безопасные примеры окружения называй `.env.example` или `.env.test.example`.

Python используется только для инструментов репозитория. Стек проекта - Go, React + TypeScript и PostgreSQL. Конкретные версии, фреймворк сервера и менеджер пакетов фиксируются отдельным согласованным изменением при появлении модулей.
