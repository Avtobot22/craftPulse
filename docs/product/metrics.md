# Метрики craftPulse

craftPulse считает два слоя показателей. Управленческий слой отвечает на вопросы руководителя и тимлида: что выпустили, как движется работа, где возвраты и насколько предсказуем план. Технический слой отвечает на вопросы техлида и разработчика: где рискованный код, кто его знает, что нашли анализаторы и как это исправить. Оба слоя строятся на одних данных и связаны переходами: от команды к задаче, от задачи к MR, от MR к проверке и находке.

Технический слой опирается на прототип, который команда собрала на хакатоне SourceCraft: сборщик истории Git, расчёт здоровья кода, горячих точек и концентрации знаний, импорт результатов AppSec и детерминированные объяснения. Формулы ниже взяты из этого прототипа и переносятся в продукт как стартовые профили, которые компания может настроить.

## Общие правила

У каждого показателя есть определение, единица, период, источник, размер выборки и время последнего обновления. По клику число раскрывается до задач, коммитов, запусков CI и находок, из которых оно получено.

Отсутствие данных не превращается ни в ноль, ни в «всё хорошо». Результат получает одно из состояний:

| Состояние | Значение |
|---|---|
| `ASSESSED` | Данных достаточно, оценка полная |
| `PROVISIONAL` | Оценка предварительная: мала выборка или проверена часть кода |
| `BOUNDED` | Известны только границы значения |
| `NOT_EVALUATED` | Проверка не проводилась |
| `UNKNOWN` | Источник вернул ошибку или неполные данные |
| `NOT_APPLICABLE` | Показатель к этому проекту не относится |

Показатели процесса не превращаются в рейтинг сотрудников. Число коммитов, строк и закрытых задач используется только на уровне команды и проекта.

## Управленческий слой

Эти показатели пришли из интервью с руководителями разработки. Денис Кучанов сейчас собирает их сам: Python-скрипт выгружает Jira, а дашборд генерируется по промпту. Даниил Романов называет те же срезы: выпуск, скорость с учётом размерности, готовность, возвраты и предсказуемость.

| Панель | Что показывает | Из чего считается |
|---|---|---|
| Выпуск | Что завершено за период, какие эпики продвинулись, объём по шкале размерности команды | Задачи и эпики трекера, связь с MR и релизами |
| Скорость и поток | Cycle time, время на каждом этапе, WIP, блокировки; всё с разбивкой по размерности и типу работ | История переходов статусов; начало и конец этапа задаются профилем workflow команды |
| Готовность | Выполнение критериев Definition of Done: ревью, тесты, регресс, интеграционное тестирование | Правила команды, результаты CI, открытые дефекты |
| Возвраты | Возвраты с регресса и с production отдельно, повторные открытия, причины | История статусов и связанные задачи-дефекты |
| Предсказуемость | План против факта в сопоставимых периодах, разброс сроков по классам размерности | Сохранённые планы спринтов и релизов, фактические даты |
| Эффект инициатив | Как изменились показатели после изменения процесса | Дата и область инициативы, сравнение периодов до и после |

Размерность задач одной команды не сравнивается напрямую со шкалой другой: сравнение команд идёт по нормированным показателям потока.

## Технический слой

### Здоровье кода

Считается по production-коду: тесты, сгенерированный код, vendor, сборочные артефакты и lock-файлы исключаются.

| Показатель | Вес | Как считается |
|---|---:|---|
| Цикломатическая сложность | 32% | Риск функции `clamp((CC - 10) / 40, 0, 1)`, взвешенный по NLOC; балл `100 × (1 - доля риска)` |
| Размер функций | 16% | Риск `clamp((NLOC - 50) / 450, 0, 1)`, взвешенный по NLOC |
| Дублирование | 20% | До 3% дублей - 100 баллов, 5% - 80, 10% - 50, от 20% - 0 |
| Маркеры техдолга | 12% | `100 × 2^(-burden / 2)`, где burden - взвешенное число TODO/FIXME/HACK на 1000 строк |
| Статический анализ | 20% | `100 × 2^(-(W / KLOC) / 5)`, где W - находки линтеров с весами critical 8, high 4, medium 2, low 1, info 0,25 |

Инструменты прототипа: Lizard 1.24.0, jscpd 5.1.2, Ruff, ESLint с typescript-eslint, golangci-lint, HTMLHint, Stylelint, ShellCheck.

Если в CI клиента уже работают линтеры или анализаторы, craftPulse не запускает их заново: шаг в CI забирает готовые отчёты (ESLint JSON, golangci-lint checkstyle, Ruff JSON, SARIF, GitLab Code Quality) и считает показатель «Статический анализ» по ним. Так учитываются правила и исключения, которые команда уже настроила. Собственный анализ остаётся для частей, где отчётов нет: сложность, дублирование, маркеры техдолга.

### Риски рядом с оценкой

Риск растёт в обратную сторону: чем выше число, тем хуже. В итоговый балл риски не входят, чтобы один сигнал не считался дважды.

| Риск | Что находит | Как считается |
|---|---|---|
| Горячие точки | Сложные файлы, которые часто, недавно и помногу меняют | `100 × structural_risk × change_pressure`; давление изменений = частота 40% + свежесть 25% + объём правок 35% |
| Зависимость от автора | Файлы, которые знает один человек (bus factor) | Доля владения = поровну доля изменений и доля строк по `git blame`; файл зависим при доле одного автора от 80% |
| Риск изменения в MR | Рискованные merge request | Размер diff 20%, число файлов 10%, горячие точки 25%, зависимость от автора 20%, нет изменений тестов 10%, состояние CI 15% |

### Процесс разработки

| Показатель | Как считается |
|---|---|
| Дисциплина слияния | 55% - доля коммитов основной ветки, пришедших через MR; 45% - доля MR, которые слил не автор |
| Скорость первого ответа | Зачёт ответа `2^(-часы / 48)`: ответ через 48 часов даёт 50 баллов |
| Работа с задачами | Завершение 50%, внимание к открытым `2^(-дни простоя / 90)` 30%, скорость закрытия `2^(-дни / 30)` 20% |
| Здоровье CI | Конфигурация 15%, доля успешных запусков 45%, свежесть `2^(-дни / 90)` 15%, длительность `2^(-минуты / 30)` 25% |

### Безопасность

craftPulse не запускает сканеры сам, а импортирует их результаты: AppSec SourceCraft (Opengrep, Trivy, kingfisher), GitLab security reports, SARIF из GitHub code scanning, отчёты внешних анализаторов. Балл `100 × 2^(-weighted / 32)` по открытым группам находок с теми же весами критичности: четыре critical дают 50 баллов. Отдельно показывается полнота проверки: сколько областей из SAST, SCA и поиска секретов просканировано.

## Динамика и объяснения

Снимки хранятся в PostgreSQL. При двух сопоставимых снимках показывается изменение, при трёх и более - наклон за 30 дней и сглаженный тренд. Смена методики или версии анализатора отмечается на графике, чтобы скачок не приняли за изменение качества.

Объяснение собирается из тех же фактов, что и расчёт: наблюдение, источник, версия правила, затронутые файлы и действие. Рекомендация пересчитывает формулу с исправленными фактами и показывает ожидаемый прирост балла. Языковая модель итоговые числа не считает.

Исключение предупреждения хранит причину, автора, область действия и срок пересмотра. Исходная находка при этом не удаляется.
