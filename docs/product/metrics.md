# Метрики craftPulse

Метрики связывают рабочий вопрос с исходными событиями и решением пользователя. Руководителю нужны завершение работы, возраст незавершённых задач и соблюдение местных соглашений. Техлиду - конкретные изменения кода, подтверждённые находки и полнота проверок. PM разбирает план, задержки и связи задачи с инженерным результатом. Для каждого из этих вопросов сохраняются формула, выборка и ограничения.

Полные каталоги содержат 122 позиции по коду, безопасности и CI/CD и 106 позиций по активности, документации и задачам. Это библиотека разных этапов, а не набор обязательных карточек первого экрана. Здесь описаны группы показателей и способы их чтения в продукте; точные контракты и ограничения приведены в шести каталогах.

| Блок | ID | Полный каталог |
|---|---|---|
| Код | C01-C36 | [01-code.md](metrics/code.md) |
| Безопасность | S01-S40 | [02-security.md](metrics/security.md) |
| CI/CD | I01-I46 | [03-cicd.md](metrics/ci-cd.md) |
| Активность | A01-A30 | [01-activity.md](metrics/activity.md) |

M0 означает основу соответствующего блока, M1 - последующее расширение, M2 - целевой сценарий или эксперимент. Сквозной пилот M0 сначала связывает задачи, MR, историю и CI. Этап конкретной строки каталога не означает, что все M0 всех блоков нужно выпустить одновременно.

Общая модель сущностей, хранение версий, состояния данных и правила сопоставимости описаны в [правилах измерения](metrics/model.md).

## Термины

Scope - явно выбранная область наблюдения: например, компонент, язык и профиль проверки. Когорта - объекты, отобранные одним правилом, например задачи с первым завершением в периоде. Evidence - исходный отчёт, событие, версия или подтверждение, на котором основан вывод. Producer - система или инструмент, выпустившие отчёт. Baseline/base - сопоставимая исходная версия, head - проверяемая версия изменения. Mapping - подтверждённое соответствие исходных полей и статусов их смыслу в расчёте.

## Общие правила расчёта

### Паспорт показателя

Карточка метрики и её выгрузка содержат один и тот же расчёт. Пользователь видит:

| Часть паспорта | Что в ней фиксируется |
|---|---|
| Определение | Стабильный ID, название, единица, версия формулы и вопрос пользователя |
| Область | Организация, проект, сервис, репозиторий, команда, типы объектов и исключения |
| Выборка | Когорта событий, окно `[from,to)`, дата состояния `as_of`, часовой пояс и календарь |
| Расчёт | Числитель, знаменатель, размер выборки, метод percentile, применимый target |
| Происхождение | Система и объект источника, запрос или правило, версия анализатора, профиля и mapping |
| Полнота | Неизвестные поля, пропущенные объекты, границы истории, состояние данных и последняя успешная сверка |
| Раскрытие | Список исходных задач, MR, интервалов, попыток или находок, из которых получено значение |

Если полный знаменатель неизвестен, показываются известное количество и ограничение охвата. Процент не достраивается предположением. Доля задач без размера, неизвестные команды, недоступные отчёты и неоднозначные связи остаются видимыми рядом с результатом.

### Состояния данных

| Состояние | Как читать |
|---|---|
| `ASSESSED` | Формула рассчитана в полном определённом наблюдаемом scope; размер выборки показан отдельно |
| `PROVISIONAL` | Доступен пригодный частичный scope или используется новый, пока несопоставимый метод |
| `BOUNDED` | Можно обосновать только границу: например, при усечённой истории известно не меньше указанного расхода повторов |
| `NOT_EVALUATED` | Источник не настроен или нужная проверка не выполнялась |
| `UNKNOWN` | Ошибка доступа, повреждённый отчёт или недостаточные данные не позволяют определить результат |
| `NOT_APPLICABLE` | Подтверждено отсутствие применимого объекта или знаменателя |

Пример неприменимости: в MR нет изменённых исполняемых строк, поэтому patch coverage не рассчитывается. Если строки есть, но coverage report отсутствует, это отсутствие измерения. Старый успешный снимок и текущая неуспешная попытка показываются раздельно.

Точность наблюдаемого count и статистическая уверенность - разные свойства. Даже точный count на малой выборке не даёт надёжной оценки следующего периода. Для p85 при `n < 20` показывается пометка малой выборки; это продуктовая защита из каталога, а не гарантия статистической достаточности при большем n.

### Время, сравнение и агрегация

Исходный timestamp сохраняется с offset, в UTC он переводится преобразованием. Для отчёта фиксируются календарь и зона команды. Календарные и рабочие дни - разные определения. Состояние на прошлую дату восстанавливается по истории; текущая команда и текущий размер задачи не заменяют исторические поля молча.

Для начального расчёта percentile применяется nearest-rank: после сортировки выбирается элемент с индексом `ceil(p × n) - 1` при нумерации с нуля. При `n = 0` результата нет. Вместе с percentile показываются n, окно и версия метода.

Сравниваются одинаковые определения, scope и сопоставимые профили. Проценты разных сервисов не усредняются без их числителей и знаменателей. Объединение допускается только при общей семантике; story points разных команд не складываются. Личный рейтинг из коммитов, строк, времени статуса и закрытых задач не рассчитывается.

Изменение результата имеет причину: код, зависимости, правила, база уязвимостей, область анализа, восстановление источника или неоднозначная идентичность. Новый advisory на неизменном артефакте не становится дефектом, внесённым последним MR.

## 1. Задачи: поток, план и готовность

Объект измерения - задача и её эпизоды работы. Ключ включает источник, instance, проект и внешний ID. Две одинаково названные задачи из разных трекеров не объединяются автоматически.

`created` - задача появилась. `started` - работа началась по подтверждённому mapping. `completed` - результат принят в workflow. `cancelled` - работа завершена без принятого результата. `delivered` - подтверждена связанная доставка. Переоткрытие создаёт следующий рабочий эпизод.

По умолчанию T05 считает уникальные задачи, у которых первое принятое завершение попало в период. T08 и T09 используют ту же завершённую когорту. Повторные завершения и доработка отражаются отдельно; они не переносят задним числом первый результат.

| Показатель | Расчёт и данные | Как использовать |
|---|---|---|
| T01-T03: спрос и backlog | Созданные задачи за окно; созданные, ещё не начатые и не terminal на дату; их возраст `as_of − created` | Разобрать входящий объём. Нужен весь открытый scope, включая старые неподвижные задачи |
| T04/T05: начато и завершено | Уникальные задачи с первым valid start или первым принятым completion в окне | Сопоставить вход в поток и результат по типу и локальному размеру |
| T06: доставлено | Задачи с подтверждённой первой delivery в окне | Отделить завершение workflow от поставки в эксплуатацию; M1 |
| T07: отмены и дубликаты | Terminal-исходы без completion по истории resolution | Не включать отмену и дубликат в выполненную работу |
| T08: cycle time | `first_completed − started`, p50/p85 и n, размер на начало | Разобрать разброс сроков завершённых задач |
| T09: lead time задачи | `first_completed − created` для той же когорты | Увидеть также ожидание до начала; это другой показатель, чем DORA change lead time |
| T10: выполнение target | Завершённые с `cycle time ≤ versioned target` / eligible завершённые | Проверить соглашение команды. Неизвестные start, size и target раскрываются |
| T11/T14: возраст незавершённого | Возраст открытого эпизода и отношение к target при его наличии | Найти задачу до завершения. Отношение к target не оценивает вероятность опоздания |
| T12: полный WIP | Задачи с открытым started-эпизодом на дату | Показать весь начатый незавершённый объём, включая blocked |
| T13/T15: блокировки | Blocked как подмножество WIP; сумма blocked-интервалов, открытый до `as_of` | Найти конкретное препятствие и длительность наблюдаемого состояния |
| T16/T17: время состояний | Непересекающиеся интервалы по классам статусов; active-state / полный cycle | Найти ожидание в процессе; M1. Это время статуса, а не измеренные часы работы человека |
| T18: баланс потока | Начато и завершено на одной шкале, рядом WIP/CFD | Изменение WIP также объясняется отменами, reopen и изменением scope |
| T19-T22: план спринта | Состав на точный start, выполнение к end, все add/remove, незавершённый остаток | M1. Removed-задача не исчезает из исходного знаменателя; add-then-remove тоже изменение |
| T23: переоткрытия | Задачи с полным follow-up окном, в котором был reopen / задачи завершённой когорты с полным таким окном | Измерить доработку workflow; свежие незрелые когорты учитываются отдельно |
| T24: возврат из gate | Задачи с согласованным backward transition / задачи, прошедшие этот gate | M1. Самый частый predecessor Done не назначается регрессом автоматически |
| T25: дефекты после поставки | Подтверждённые production defects, связанные с delivered cohort / delivered tasks | M1. Число дефектов показывается отдельно; несколько дефектов одной задачи могут дать отношение выше 100% |
| T26/T27: DoD | Покрытие машиночитаемыми обязательствами; доля eligible completed с подтверждением всех обязательств | M1. Тесты, безопасность, документы и ручная приёмка имеют evidence на нужную версию |
| T28/T29: связи и зеркала | Подтверждённые task↔merged MR для обязательных типов; группы зеркал и конфликты полей | M0 для связей с MR, M1 для нескольких трекеров. Нет fuzzy-склейки по названию |
| T30-T36: бизнес и доработка | Подтверждённые связи с инициативой, mix работ, срок эпика, зависимости, передачи, completion→delivery lag и rework episodes | M1. Count, местный размер и elapsed duration не переводятся в выручку или человеко-часы |
| T37: прогноз | Распределение сроков/объёма по историческим throughput samples с backtest | M2. Сценарий с условиями стабильности процесса, без гарантии дедлайна |
| T38-T42: доверие к данным | Полнота каждого поля, истории и mapping, watermark/lag, расхождение с исходной выборкой | Показываются вместе с управленческими выводами |

Target выбирается командой по размеру и типу. Исторический p85 - исходный ориентир с периодом, n и полнотой, а не автоматически обязательный срок. Изменение target сохраняется новой версией и не переписывает старые нарушения.

Полный WIP включает blocked, waiting и active по согласованной модели. Пауза может исключаться из отдельного active-clock, но остаётся в полном времени прохождения. Начало не исключается только потому, что совпало с созданием задачи.

Исходный план спринта фиксируется на фактический start по sprint ID. При полной истории состава и метаданных возможен backfill. Иначе продукт собирает снимки с подключения, а старый исходный план остаётся неизвестным. Закрытие всех тикетов не доказывает достижение цели спринта.

## 2. Активность: события и ожидание взаимодействия

Блок активности восстанавливает ход работы и показывает очередь. Человеческие действия, боты и системные события отделяются. Один webhook может описывать уже известное действие; повторная доставка не увеличивает показатель.

| Показатель | Расчёт и данные | Как использовать |
|---|---|---|
| A01-A04: контекст изменений | Уникальные достижимые SHA, изменённые пути, additions/deletions, доля наблюдаемых полных недель с человеческим изменением | Диагностика репозитория. Squash и rebase меняют числа; строки и коммиты не измеряют полезную работу |
| A05/A06: очередь MR | Открытые не-draft MR и возраст `as_of − ready_at` для ещё не получивших человеческое ревью | Разобрать ожидающие изменения; при отсутствии ready-события proxy от открытия подписывается явно |
| A07: первый ответ | `first qualifying human review − ready_at`, p50/p85 и n | Автор MR и бот исключаются. Если API даёт только notes, название - первый внешний ответ |
| A08: ответ в срок | MR с ответом до порога / MR с полным окном наблюдения | M1. Молодой MR не объявляется нарушившим срок до окончания окна |
| A09-A14: ревью после ответа | Интервалы до merge, раунды, resolvable threads, ожидание повторного ревью и автора | M1. Обычный комментарий не считается blocker; число обсуждений не заменяет число раундов |
| A10: нет reviewer | Ready open MR без назначенного reviewer / ready open MR | Действие по маршрутизации. Недоступное поле не означает, что reviewer не назначен |
| A15-A17: концентрация и зоны | Доли ревью у top-участников, очередь по service/team, концентрация файловых изменений | M1. Сигнал зависимости для разбора, без вывода о компетентности или незаменимости |
| A18/A20: трассировка | Связанные merged MR / eligible merged MR; задачи обязательных типов с task→MR цепочкой / такие задачи | Показать охват связей с обеих сторон. Для research/ops допустима неприменимость |
| A19/A21: контекст и пробелы | Явные doc-связи и обязательные изменения без task-link | M1. Отсутствие ссылки не становится обвинением в скрытой работе |
| A22: история дня | Дедуплицированные события по дню и типу, human/system/bot отдельно | Восстановить эпизод с переходом к исходному объекту |
| A23/A24/A27/A28/A30 | Lag событий, полнота страниц и истории, watermark, actor-kind, подтверждённые и неоднозначные связи | Проверить, можно ли опираться на таймлайн и очередь |
| A25/A26/A29 | Межкомандные передачи M2, добровольный pulse M2, историческая привязка service/team M1 | Расширения с отдельными данными и правилами публикации |

Открытая очередь и длительности уже завершённых ревью - разные выборки. Улучшение p85 первого ответа не скрывает MR, которые пока не получили ни одного ответа. Для одного изменения сохраняются версия diff и обстоятельства ожидания; время состояния не приравнивается к личному бездействию.

## 3. Код: структура, изменения и долг

Из Git получаются дерево, diff и история. Из API - MR и связи; из анализаторов - детальные находки, функции и clone ranges. Для каждого компонента, языка, вида анализа и профиля выбирается источник. Внешний полный отчёт на нужный SHA имеет приоритет для покрытой им области.

Production-scope исключает generated/vendor/build/cache/binary; тестовый код учитывается отдельно. Security-scope настраивается самостоятельно: lockfiles, конфиги и примеры могут быть нужны для SCA и поиска секретов.

| Показатель | Расчёт и данные | Как использовать |
|---|---|---|
| C01-C03 | Production NLOC, охват файлов по языку/инструменту и доля завершённых requested scopes | Объём и достаточность анализа; число строк не означает производительность |
| C04-C07 | CC функции и p50/p90/max, доля функций выше настроенного порога, длина NLOC и параметры | Найти сложные места для ревью; параметры - M1. CC разных движков и cognitive complexity не взаимозаменяемы |
| C08/C09 | Объединение дублированных диапазонов / eligible analyzed physical lines; clone groups | Не считать пересечение дважды. Группа копий не разворачивается в отдельный долг для каждой пары файлов |
| C10 | Native cognitive complexity анализатора | M1. Сохраняются единицы и источник |
| C11-C14 | Открытые actionable findings, новые и устранённые на сопоставимой базе; плотность на KLOC M1 | Раскрыть правило, файл и исходную критичность; accepted/FP учитываются отдельно |
| C15-C17 | Added/deleted lines и changed files раздельно, delta CC сопоставленной функции, новые clone groups | Оценить именно изменение MR. Rename или разбиение функции требуют mapping |
| C18-C23 | Касания и churn, их концентрация, hotspot shortlist, co-change и author contribution | Базовые факты M0; hotspot/coupling/ownership M1, межкомпонентный co-change M2. Ownership - proxy по истории, а не доказанный bus factor |
| C24-C27 | Возраст находки, new−resolved backlog, исключения и TODO/FIXME/HACK | Разобрать открытый долг и причины его изменения. Комментарий TODO не нарушает качество сам по себе |
| C28/C29 | Patch line coverage; изменённые функции без сопоставленного покрытия M1 | C28 = I27. JUnit не содержит line coverage; отсутствие mapping отделяется от непокрытых строк |
| C30/C31 | Latency human review и доля findings с явной задачей | M1. Подсказка по ключу не равна подтверждённой relation |
| C32/C33 | Воспроизводимость оснований рекомендаций; действия по cohort предупреждений M1 | Проверить продуктовый результат и шум, без оценки дисциплины сотрудника |
| C34-C36 | Native remediation effort M1, свежесть complete snapshot и расход анализатора | Условные минуты инструмента не считаются трудозатратами команды |

Новой считается head-находка, которая после сопоставления идентичности не найдена в сравнимом base. Без такой базы используется «впервые наблюдена». Исчезновение из отчёта считается устранением только при полном сопоставимом scan; timeout, исключение файла или отключённый анализатор не закрывают проблему.

Стартовые ориентиры сложности и длины - параметры пилотного профиля. Они помогают сортировать ревью, а не заменяют инженерную оценку и не дают доказанную вероятность бага. Сводная формула здоровья из весов прототипа в этот набор не входит.

## 4. Безопасность: находки вместе с областью проверки

Матрица наблюдения различает SAST, SCA, secrets, IaC и image scan. Успешная job, включённый движок и полный scan - разные факты. Найденный потенциальный секрет передаётся с редактированным evidence; исходное значение не попадает в выдачу.

| Показатель | Расчёт и данные | Как использовать |
|---|---|---|
| S01-S08 | Последний complete run по component/SHA или digest/kind/profile, file coverage, resolved dependency versions, глубина secrets history, свежесть DB и scan | Проверить охват. Доля актуально проверенных production digests S06 - M1 при deployment inventory |
| S09-S12 | Открытые actionable occurrences, новые и verified fixed, CWE/rule и native confidence | Триаж конкретных проблем. SARIF level не переводится в CVSS простым переименованием |
| S13/S14 | Уникальные affected package instances и advisories с подтверждёнными aliases | Различить затронутые зависимости и публикации об уязвимостях |
| S15/S16 | Instances с известной исправленной версией / instances с известной fix metadata; проблемы введённых зависимостей | Отдельно unknown/no-fix. Обновление версии не гарантирует совместимость |
| S17-S20 | Occurrences образа по digest, IaC rule/resource, redacted secrets; подтверждение/отзыв секрета M1 | Удалённая строка не доказывает отзыв credential; проверка у провайдера отдельна |
| S21-S25 | KEV, EPSS, reachability, exposure и затронутые deployed services | M1/M2. Каждый сигнал со своим evidence; неизвестная достижимость не становится безопасностью |
| S26-S30 | SBOM, лицензии, подпись и provenance по связанному артефакту | M1/M2. Наличие файла не равно успешной проверке подписи, полноте inventory или юридическому заключению |
| S31-S34 | Возраст открытого, verified-fix time, время human triage, превышение локальной policy | Возраст M0, остальные M1. Рядом с закрытой когортой остаются незакрытые проблемы |
| S35-S38 | Scoped исключения, повторное появление verified-fixed, решения триажа и новые данные DB/rules | Исключения и причины DB/rules M0; остальные M1. Распределение решений не измеряет истинную precision сканера |
| S39/S40 | Missing-поля приоритизации; release decisions с failing required check и bypass | M1. Авторизованный waiver и несанкционированный bypass раздельны; S40 использует те же решения, что I45 |

Критичность, уверенность producer, достижимость и exposure хранятся раздельно. Их нельзя молча перемножить и назвать вероятностью взлома. Свежесть базы также видна отдельно от числа findings. Обновлённая DB может обнаружить новую известную проблему в прежнем digest без изменения кода.

Accepted risk и false positive имеют автора, причину, scope и срок пересмотра. Они сохраняются в истории, не переименовываются в исправление и не подавляют всё правило для всей организации.

## 5. CI/CD: исход, попытки, тесты и доставка

Единицы наблюдения разделены: logical pipeline run, logical check, job attempt, test case/configuration, report, build artifact и deployment. MR, main/push, scheduled/nightly, release и manual считаются отдельными когортами. Default branch берётся из metadata источника.

| Показатель | Расчёт и данные | Как использовать |
|---|---|---|
| I01/I06 | Terminal success / (success + failed + timeout + unstable по mapping); все исходы рядом | Canceled, skipped и manual не исчезают из распределения исходов |
| I02 | Checks с успехом на первой попытке / checks с известным first outcome | Сопоставить с финальным успехом; полнота первых attempts видна |
| I03/I04 | Сопоставимые checks с fail→pass / checks с complete attempts; лишние attempts и их execution time | Найти observed retry flip и расход повторов. Это не доказанный flaky-тест |
| I05 | Successful runs с финально failed `allow_failure` job / successful complete runs | Показать разрешённый провал отдельно от восстановившейся попытки |
| I07-I10 | Причины failure, missing required checks, missing/invalid reports, completeness импорта | Unknown-причина не приписывается коду. Без expected policy неизвестен полный список обязательных проверок |
| I11/I12 | `finished − started`; `finished − created` отдельно; очередь по native timestamps | Разделить выполнение, общую задержку и ожидание runner |
| I13/I14 | Сумма execution durations всех attempts в job-min; critical path по DAG M1 | Параллельные job-min не равны wall duration или billed minutes |
| I15-I18 | Первый actionable failure, time to green M1, nightly по suite/config, стоимость по rate card M2 | До известных ставок показывается расход, без выдуманной валютной экономии |
| I19-I24 | Pass/fail/error/skip, distinct cases и executions; mixed outcomes сопоставимого case/env; duration tail, stable-suite progress M1, skipped/quarantine debt M1 | Один тест в нескольких matrix-конфигурациях не становится несколькими новыми тестами; skipped не доказывает quarantine |
| I25/I26 | Covered executable lines / executable lines; covered branches / reported branches отдельно | Единицы и scope отчёта сохраняются; line coverage не заменяет branch coverage |
| I27/I28 | Покрытые changed executable lines / changed executable lines с mapping; доступность самого coverage mapping | C28 = I27. Неизвестный язык/файл не получает автоматический ноль |
| I29/I30 | Ресурс повторов с подтверждённой test-failure причиной M1; test-to-code instrumentation M2 | Не весь расход failed-job относится к тестовой нестабильности; JUnit недостаточно для test selection |
| I31-I36 | Config validation, опасные patterns M1, immutable refs M1, required evidence, overhead craftPulse, artifact linkage M1 | Полнота обязательных проверок и ресурс самого продукта видны отдельно |
| I37/I38 | Успешные production deployments за окно; первый successful prod deploy с change минус commit time | M1. Release tag, сборка и закрытый тикет не заменяют deployment |
| I39-I42 | Deployment-caused change failures, время восстановления, незапланированные deployments из-за incident, rollback | I39-I41 - M2; rollback I42 - M1. Нужны подтверждённые связи и причины |
| I43-I46 | Связность digest/source/checks, required scans до deploy, waiver/bypass и полнота CD outcome/change/incident mapping | M1. Поздний scan не делает старый release gate пройденным |

Пять delivery-измерений DORA в техническом каталоге - I37-I41: частота deployments, change lead time, change fail rate, failed deployment recovery time и deployment rework rate. Они включаются по наличию данных и своему этапу, без подмены метриками задач или общим MTTR любых инцидентов.

Повторное исполнение сравнивается только при сопоставимой logical-check identity, commit и конфигурации. Совпадение имени job не объединяет разные matrix/stage-проверки. Test instability требует идентичности теста и исполнения; сводка JUnit без attempts даёт только наблюдаемые результаты.

## 6. Документация: конкретные обязательства сервиса

Источниками могут быть Git, отдельный документационный репозиторий, wiki или разрешённый экспорт. Пользователь выбирает roots, сервисы, владельцев, аудиторию и профиль. Для внутреннего API, публичной библиотеки и production-сервиса набор обязательств различается.

| Показатель | Расчёт и данные | Как использовать |
|---|---|---|
| D01/D02 | Число обнаруженных roots/успешно прочитанных документов; доля распарсенных доступных форматов M1 | Процент всех документов компании считается только при полном manifest |
| D03-D05 | Документы с валидным owner, подтверждённым назначением/аудиторией; сервисы с доступным doc root / eligible сервисы | Последний редактор не назначается владельцем автоматически |
| D06/D07 | Сервисы с требованиями onboarding-profile; production-сервисы с owner-assigned runbook | Наличие разделов не доказывает успешный запуск или готовность к инциденту |
| D08/D09 | Просроченный review по due-policy M1; возраст content change | Изменение timestamp не считается review, старый стабильный контракт не становится ошибкой по возрасту |
| D10/D11 | Подтверждённо отсутствующие local file/anchor; устойчивые 404/410 разрешённых внешних targets после проверки | 403, 429, timeout и недоступная сеть классифицируются отдельно |
| D12/D13 | Orphan-кандидаты по выбранному графу; нарушения конкретных структурных правил | M1. Документ с прямой ссылкой из задачи может быть полезен вне меню |
| D14-D16 | Структурно непустые API-descriptions; связанные examples M1; report проверки example на ту же версию M1 | У операций и параметров разные знаменатели. Code fence не подтверждает работоспособность примера |
| D17-D19 | Нарушенное обязательство обновить reference, review текущего hash, время verified исправления | M1. Любая правка кода не порождает обязательство переписать документацию |
| D20-D22 | Task/doc-связи обязательных типов; подтверждённые handover-обязательства M1; ADR по реестру решений M1 | Для остальных типов N/A. Полный реестр решений не выводится из названий MR |
| D23-D25 | Совпадение опубликованного комплекта с версией релиза M1; валидность specs; guide для confirmed breaking change M1 | Schema-valid не доказывает соответствие реализации; latest main не всегда версия релиза |
| D26 | Успешные согласованные runbook exercises / проведённые exercises | M2. Operational readiness требует выполнения, а не только текста |
| D27-D30 | Полнота/свежесть корпуса, scoped исключения M1, подтверждённые дубли/противоречия M1 и типизированный doc debt | Полнота сбора не равна актуальности содержания; похожесть - кандидат на review |
| D31-D34 | Неуспешный поиск, подтверждённое нахождение ответа, явная полезность и повторные обращения | M2 с отдельной телеметрией и согласованными задачами. Просмотры и клики не заменяют успех |

Минимальная Git-панель использует доступные D01, D03-D07, D09-D11, D20, D27, D30 и проверки OpenAPI. Без настроенного root не появляется «0% документации». Семантическая модель может предложить связь или противоречие, но неподтверждённое предложение остаётся на review и не меняет обязательный pass/fail.

## Как читать несколько показателей вместе

Ниже учебные ситуации, а не результаты замеров клиента.

**WIP с блокировками.** Если на дату начаты и не завершены 10 задач, а 3 из них заблокированы, полный WIP равен 10, blocked - 3. Значение 7 описывает остальные задачи, а не весь поток. Для каждой из трёх раскрываются интервалы и известная причина блокировки.

**Зелёный CI.** Проверка на том же SHA прошла после последовательности fail→fail→pass. Финальный исход успешный, first-pass неуспешный, лишних attempts две. I03 показывает смену результата, I04 - расход повторов. Причина может быть инфраструктурной; без test evidence название flaky не присваивается.

**Закрытая задача и поставка.** В периоде есть принятое completion, затем reopen и повторное completion. T05 учитывает первый результат в его периоде, доработка отражается эпизодом. Пока нет подтверждённого deployment/release-link, T06 не объявляет задачу доставленной. Reopen сам по себе не становится production defect.

**Новые данные безопасности.** На том же digest появилась CVE из новой DB. Это новая известная проблема прежнего артефакта с причиной DB change, а не автоматически ухудшение последнего MR. Отдельно видны затронутая зависимость и freshness базы.

**Недоступная документация.** Внешняя ссылка вернула 403. Это access denied в наблюдаемой области, а не подтверждённый broken link D11. Пользователь проверяет доступ runner или разрешённый corpus; метрика не штрафует содержание неизвестной страницы.
