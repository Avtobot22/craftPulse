# Метрики активности и взаимодействия

## Продуктовое решение

Штатный блок активности - объяснимая история работы проекта: что изменилось, где ждут взаимодействия, как изменение связано с задачей, проверками и выпуском. Он помогает руководителю восстановить контекст и устранить очередь. Число коммитов остаётся описательной статистикой. Рейтинг продуктивности сотрудников из событий не строим.

В первом экране показываем таймлайн выбранного дня, очередь ожидающих MR, время до первого человеческого ревью, связь MR с задачами и полноту источников. Метрики потока задач принадлежат [блоку задач](tasks.md); состояние CI - [блоку CI/CD](ci-cd.md). Здесь нет второго расчёта тех же показателей с иной формулой.

Это проект целевого поведения, а не описание уже работающих интеграций. В текущем коде есть оценка регулярности Git-истории; полноценной истории GitLab + Jira + Confluence пока нет. Подробности аудита - [в проверке реализации](../../research/interview-report.md).

## Штатная реализация по умолчанию

### Сбор и нормализация

1. При подключении пользователь выбирает проекты, ветку интеграции, команды и временной диапазон. Сервис делает read-only discovery и показывает capabilities до первого числа.
2. Git-история и entity API дают backfill. Webhooks ускоряют появление событий; ночная сверка восстанавливает пропуски. Дашборду достаточно ежедневного обновления, MR-проверке нужен ответ в пределах CI-задачи. Это два режима доставки, а не требование realtime ко всей системе.
3. Сохраняем `tenant/source/entity/event_id`, `event_time`, `observed_at`, `actor_id`, `actor_kind`, `action`, `before/after`, ссылку, версию схемы, ограничения видимости. У разных источников независимые курсоры и watermark.
4. Удаление, force push, закрытие и новое открытие - явные изменения. Повтор webhook не создаёт второй MR. Rebased коммит может иметь другой SHA; никогда не считаем SHA универсальным идентификатором результата работы.
5. Пользователь подтверждает сопоставление учётных записей. Боты, сервисные аккаунты, зеркала, импортированные и системные события помечаются. Совпадение display name не склеивает двух людей.
6. Связь задача↔MR: явный API link > подтверждённый ключ/URL > предложенная эвристика. У каждой связи тип, основание, уверенность и подтверждение. Вероятностные связи не попадают в обязательную оценку DoD.
7. Расчёт метрик по версионируемым определениям. По умолчанию UTC в хранении, календарная зона проекта в агрегации, календарные часы в длительностях. Business-hours вариант - отдельная метрика с календарём и версией.

В пилоте не нужны LLM и содержание личных комментариев: достаточно метаданных, статусов и явных ссылок. Для summary модель может получить разрешённые агрегаты и ссылки; её текст не становится первичным фактом.

### Как выглядит экран

Сверху: дата/период, команда, сервис, бизнес-эпик, freshness и непокрытые источники. Далее три области: «Изменения за день», «Где ждём взаимодействия», «Как это связано с задачами». Из карточки открывается цепочка задача → MR → проверки → выпуск → документация. В контексте MR показываем только относящиеся к нему ожидания и факты.

Пример сообщения: «В очереди 7 готовых к ревью MR; 3 ждут первого человеческого ответа более командного ориентира 24 календарных часа. У двух нет назначенного reviewer. Данные GitLab до 08:00; Jira ещё обновляется». Порог 24 ч - пример настройки, не универсальная норма.

### Правила длительностей и когорт

Для A07 публикуем две выборки: завершённые ответы за период и текущую очередь без ответа. Первая отвечает «как отвечали», вторая - «что горит сейчас». Нельзя делать вид, что быстрая обработанная часть описывает все ещё ожидающие MR. Когорта по ready_at подходит для соблюдения target; неполные окна явно цензурированы.

Draft→ready→draft→ready сохраняется эпизодами. Для первого ответа используем первый валидный ready эпизод, для ожидания повторного ревью - новые эпизоды. Перевод в draft приостанавливает только договорённый ready-clock, но не скрывает полный календарный возраст. Отдельные определения не смешиваем в одном тренде.

## Пользовательские сценарии и проверка ценности

**История дня с доказательствами.** На вопрос Кучанова «что происходило в эту дату» открываются события всех разрешённых систем, сгруппированные по задаче, а не тысячей webhook. AI-резюме ссылается на группы и умеет сказать «история Confluence недоступна». Проверка: руководитель быстрее восстанавливает 3 заранее выбранных эпизода; измеряем время и ошибки против его нынешнего процесса.

**Объяснение ожидания MR.** Сопоставляем ready/review интервалы, CI jobs и blocker-связи задач. «MR ждёт 31 ч; CI завершён 28 ч назад; reviewer не назначен» - наблюдаемые факты. «Техлид перегружен» - только гипотеза. Проверка: доля алертов, после которых произошло полезное действие, и время сокращения очереди в сопоставимых когортах.

**Сигнал узкого знания с планом проверки.** Концентрация изменений/ревью + критичность сервиса + отсутствие свежего runbook → карточка риска и предложение парного ревью/проверки инструкции. Вывод о bus factor требует подтверждения команды. Проверка: появился резервный владелец, успешно выполнивший runbook exercise; не просто стало больше reviewers.

**Контекст при входе в проект.** Из списка активных эпиков, последних изменений, владельцев и документов строим обзор со сроком актуальности. Это отвечает сценарию Micha; не обещаем автоматического понимания архитектуры.

## Этапы и приёмка
