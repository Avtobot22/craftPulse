# Адаптер GitLab self-managed

`adapter-gitlab` принимает базовый HTTPS-адрес GitLab и области вида `repository`. В каждой области указывают глобальный числовой ID проекта. Служебной учётной записи нужны токен со scope `read_api` и роль Reporter в закрытых проектах. `Probe` проверяет версию, редакцию и доступ к проекту, членству и истории MR. Для ключа экземпляра берётся ID источника, когда он доступен, или нормализованный базовый адрес. Проверенный адрес хранится вместе с привязкой к текущему токену в БД адаптера. После замены токена требуется повторный `Probe`. [Проверка на стенде #91](https://github.com/Avtobot22/craftPulse/issues/91)

`Fetch` с видом `merge_requests` возвращает репозиторий, MR, ревизии diff, события и записи их участников. Для MR используется глобальный `id`, а `iid` нужен для адресного запроса внутри проекта. Вид `accounts` выгружает участников проекта. Почта попадает в пакет, когда её GitLab показывает сборщику. `Manifest` возвращает глобальные ID и `updated_at` MR за период.

Для истории адаптер обходит `discussions`, `resource_state_events` и `versions` по `X-Next-Page` или `Link rel="next"`. Время перехода из draft в ready берётся из `created_at` системной заметки с текстом `marked this merge request as **ready**`. Если заметка пришла без времени, запись получает `event_time_unknown`. Она сохраняется в пакете, а расчёты помечают историю MR неполной. Для push адаптер связывает системную заметку с ревизией по `diff_id` и берёт автора и время из заметки. Если такая заметка отсутствует, доступно время ревизии diff. [Исходный код системных заметок GitLab](https://gitlab.com/gitlab-org/gitlab/-/raw/master/app/services/system_notes/merge_requests_service.rb)

Между страницами MR адаптер продолжает с пары `updated_at` и глобального `id`. При новом проходе ядро сдвигает нижнюю границу назад, чтобы повторно прочитать изменившиеся объекты. Сверка идентификаторов и времени через `Manifest` выявляет пропуски, оставшиеся из-за изменения списка во время обхода.

## Pipelines, попытки и отчёты

`Fetch` с видом `ci_runs` читает данные вида `ci` в области `repository`. Страница содержит один pipeline и его попытки. `Manifest` возвращает глобальные ID и `updated_at` pipelines за тот же период. Для обоих методов порядок задаёт пара `updated_at` и глобального ID. Ядро сдвигает курсор на 10 минут назад при новом проходе. Изменение `updated_at` после retry возвращает pipeline в выборку, где адаптер читает все попытки заново.

GitLab выдаёт обычные и дочерние pipelines разными списками. Адаптер объединяет списки по одному курсору. Связь с родителем и MR берётся из API GitLab. Для дочернего pipeline адаптер сопоставляет ID с `downstream_pipeline` в trigger jobs родителя. Если trigger job уже заменена повтором, используется исходная связь `sourceJob`, которую вернул GitLab.

Запрос jobs передаёт `include_retried=true`. Номер попытки определяется по `created_at`, а при совпадении времени - по ID job. Имя вида `test: [linux]` даёт ключ `test` и отпечаток значений матрицы. Имя вида `test 1/2` даёт отпечаток по индексу `1`. `native_status` и `failure_reason` сохраняют значения GitLab. Если страница jobs недоступна или в одном pipeline больше 1000 попыток, запуск получает отметку `selection.truncated`. При обрыве истории номера отражают доступный набор попыток.

JUnit, Cobertura и JaCoCo скачиваются по ID job через `artifacts?file_type=…`. Для gzip GitLab адаптер распаковывает поток и считает SHA-256 байтов XML, которые вошли в пакет. Лимит - 8 MiB на файл, 16 MiB на страницу и до 900 файлов на страницу. Если файл истёк, недоступен или превышает лимит, попытка сохраняется с `artifact_status`. [GitLab Pipelines API](https://docs.gitlab.com/api/pipelines/) · [GitLab Jobs API](https://docs.gitlab.com/api/jobs/) · [GitLab Job Artifacts API](https://docs.gitlab.com/api/job_artifacts/)

На стенде GitLab 19.5.5 повтор уже завершённой timeout job создал новую попытку и сдвинул `updated_at` pipeline 7 с `15:03:24.172Z` до `15:05:58.207Z`. Отдельный прогон матрицы сохранил исходную упавшую попытку Linux после успешного retry. API отдал JUnit и Cobertura как gzip с `Content-Type: application/octet-stream`. Для job с истёкшим сроком хранения после очистки артефактов API вернул HTTP 404, а сама job осталась в перечне попыток.

## Сборка и тесты

Команда сборки из `backend/`.

```sh
go build ./cmd/adapter-gitlab
```

Контрактные тесты запускаются с PostgreSQL в Docker. Тестовый HTTP-сервер воспроизводит пагинацию и ошибки GitLab, включая обрыв страницы истории.

```sh
go test ./internal/app -run 'TestContract_GitLabAdapter|TestGitLabAdapter'
```
